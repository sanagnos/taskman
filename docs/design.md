# Design decisions

Why taskman works the way it does. Read this before changing one of these areas: several choices look like they could be simpler, and were made for a reason that isn't visible in the code. What is where in the code is in [architecture.md](architecture.md).

## Claude runs as the real CLI in a pseudo-terminal

Each pane is the `claude` binary in a PTY (`portable-pty`), drawn through a vt100 emulator (`vt100` + `tui-term`). taskman implements tui-term's screen traits itself (`term.rs`) rather than use its `vt100` feature, which would hold vt100 to the version tui-term asks for. The alternative was the Claude Agent SDK, or `claude -p` with stream-json, and drawing our own chat UI. That would give structured events, but lose everything interactive: `/config`, the model picker, `/resume`, permission prompts, plan mode, plugins and keybindings. Keeping the real CLI means every Claude Code feature works on day one and keeps working as Claude Code changes. The price: taskman only sees a screen, so anything it needs to know comes from hooks or from reading that screen.

`session.rs` answers the terminal queries a real terminal would (cursor position, device attributes, colour queries) and forwards OSC 52 clipboard writes; without the replies Claude Code can stall or misjudge the terminal.

Nothing writes to a session's pty but a thread of its own (`Input`): keys, pastes and those replies are queued for it and the caller goes on. Writing them where they came from, the UI thread and the reader, froze taskman for good: a long paste to a CLI that read slowly and asked for the cursor as it did held the UI thread on the write, the reader on the writer's lock and the CLI on its own output. Alacritty and WezTerm write from a loop or thread of their own too. The queue holds 4 MB at most; past that, what's typed or pasted is dropped with a toast, rather than taken by a CLI that isn't reading. The thread ends once the session and its reader are gone (a write to a pty whose CLI has ended fails at once).

## Status comes from hooks, passed with `--settings`

taskman needs to know when each session is working, waiting for permission, or done. It starts `claude` with `--settings '<json>'` adding hooks (SessionStart, UserPromptSubmit, Pre/PostToolUse, PermissionRequest, Notification, Stop, SessionEnd) that run `taskman hook <state>`. That writes a small JSON status file, which the TUI polls every 300 ms. One struct (`status_file::Record`) is the file for the hook and every reader, so they read it alike: a field that's missing or holds something else reads as its default, and a state a newer release added reads as idle. Passing hooks on the command line means the user's own settings files are never edited, and sessions started outside taskman are unaffected.

The hook also records the session id, which is how a ticket resumes its conversation after a restart (`--resume <id>`, only when the transcript still exists).

Each start of a session gets an id of its own (`TASKMAN_LAUNCH`, `launch::launch_id`), which the hook writes into the record, and the pane takes a record only from the start it runs (`TicketView::takes`). A CLI runs its SessionEnd hook on the hangup that stops it, and the hook outlives the kill that follows a moment later, so its record lands after taskman has removed the status file: taken, it would show a restarted session as ended, or hand a ticket that was closed and added again its old conversation to resume. Adding a ticket or agent, and starting a session, clear the file too, so a record left behind can't pass for the session's latest conversation at taskman's next start (`take_leftover_status`). Outside (`taskman resume`), whatever the hooks write is the session's.

Hooks fire at the moment something happens, so they decide the state wherever one exists:

- **Working:** UserPromptSubmit and PreToolUse.
- **Needs you, permission:** PermissionRequest, in Claude and Codex. Claude's fires about 50 ms after its prompt appears; its `Notification` (`permission_prompt`) comes 6 to 7 s later, and only if the prompt still waits. taskman takes both: PermissionRequest for the moment, the notification for Claude versions and clients without PermissionRequest. The hook writes `reason: permission`.
- **Needs you, question:** PreToolUse of `AskUserQuestion` and `ExitPlanMode` (Claude) and `request_user_input` (Codex), written as `reason: question`. Claude also fires PermissionRequest and, 6 s later, `Notification(permission_prompt)` for these, so a notification that arrives while the file already says "needs" keeps the reason and message there (`hook::entry_for`); the notification's type alone can't tell a question from a permission prompt.
- **Back to working after questions:** PostToolUse, 13 to 41 ms after the last answer is submitted. Answering question 1 of 3 fires nothing, and neither does the final review screen until it is submitted, so nothing but that hook clears a question.
- **Your turn:** Stop, and Codex's Interrupt.
- **After a compaction** Claude fires SessionStart with `source: "compact"`; the hook keeps the state it had, since an automatic compaction happens in the middle of a turn.

### Inferred states

Four things fire no hook, and one hook fires before it's known whether it needs the user, so taskman infers them from keys and the screen. Each rule is a pure function with its tests: `app::poll::prompt_key` for keys, `app::poll::inferred_state`, `app::poll::review_step` and the `Cli` methods that read a screen (`approver`, `asks_trust`) for the screen. Measured with Claude Code 2.1.296 and Codex 0.162 on Linux (WSL), each in a private tmux server with a hook logging every event and a pipe timing every output chunk.

- **A permission prompt answered.** Neither CLI has a hook for an approval. The next event is PostToolUse when the tool finishes: 31.5 s (Claude) and 39 s (Codex) after approving a 30 s build, all of it shown as "needs you". So when the status says `reason: permission`, a key that answers the prompt switches the session to working at once (`Status::key`):
  - Claude: Enter, Esc, ctrl+c and a digit (a digit picks its option at once). Arrows only move between options. Tab opens a field for adding to the answer, where digits and letters are text ("1n" became "Yes, 1n"), so after Tab only Enter and Esc count.
  - Codex: Enter, Esc, ctrl+c, `y` and `n`. `p`, `a` and digits are options on some prompts only; one that isn't an option does nothing, so they're left out and those answers show when the next hook fires. Declining (Esc or `n`) fires Codex's Interrupt hook within 25 ms.
  - Questions and plans (`reason: question`), and records written before `reason` existed, are never cleared by a key.
  - Declining a Claude prompt (Esc, or "No") ends the turn with an "Interrupted · What should Claude do instead?" line and no hook, within 300 ms. So the key also starts the watch for a new "Interrupted" line, which means "your turn".
  - A key that didn't answer leaves the prompt waiting, and a waiting Claude prompt draws nothing, while an approved one starts the spinner at once. So 2 s of quiet after the key (`QUIET_AFTER_KEY`) puts the session back to "needs you", never "your turn": the silence rule doesn't apply until the next hook. (A waiting Codex prompt redraws every second, which is why Codex counts only keys that always answer.)
  - Hooks stay authoritative: every hook event replaces what was inferred. Claude's 6 s notification is sent only for a prompt still waiting (it never came for one answered within 1 s), so it can't undo a real approval.
- **Codex's reviewer deciding an approval.** With Codex's automatic reviewer on (`approvals_reviewer = "auto_review"`, or "Approve for me" in `/permissions`), Codex still runs the PermissionRequest hook for every approval request, then gives the request to the reviewer, which can take up to 90 s. Approving fires no hook until PostToolUse when the command ends, and declining fires none, so "needs you" would last minutes, with a bell and a notification for nothing; Codex itself notifies only for prompts it puts to the user. So a Codex permission record doesn't make the session "needs you" at once (`Status::hold`): it shows working, with no bell or notification, while each poll reads the screen (`Cli::approver`):
  - Codex's status line reading "Reviewing approval request" (or "Reviewing 2 approval requests") means the reviewer has it: still working.
  - Codex's prompt, told by its footer ("Press enter to confirm or esc to cancel"; its other lists say "to go back"), means the user has it: "needs you", the bell and the notification, at once. A waiting Codex prompt redraws every second, so its text, not quiet, is what tells.
  - Neither within `REVIEW_WAIT` (1 s) of the hook means no reviewer took it: "needs you", a second later than the hook. The reviewer's line shows as soon as the hook has run.
  - Once the reviewer's line has been gone for 1 s with no prompt, the reviewer approved (the command runs) or declined (Codex goes on), and the screen isn't read any more. A reviewer that gives up (its input too large) hands the request to the user as its line goes, which the prompt catches.
  - Reading `approvals_reviewer` from Codex's config was rejected: profiles set it, `/permissions` changes it mid-session, and the reviewer can still hand a request to the user.
  - Checked with Codex 0.162.1 approving commands that needed the network: the reviewer's line showed for about 3 s, the status file said "needs" until PostToolUse (1.9 s on one run), and the sidebar stayed "working" throughout. Any hook replaces what was held.
  - A session running outside (`taskman resume`) has no screen in taskman, so no reviewer's line can show: its request needs the user once `REVIEW_WAIT` is up, as with no reviewer.
- **A CLI asking to trust its folder.** In a folder it hasn't been told to trust, Claude Code asks "Quick safety check: … Yes, I trust this folder" (once per repository: a worktree's trust is its main repository's) and Codex asks "Trust this folder? … 1. Trust and continue", each before any hook runs, SessionStart included, so the status folder holds only the owner file. So until a session's first hook, each poll reads its screen for the question (`Cli::asks_trust`, `Status::trust`): while it shows, the session needs you ("asks to trust its folder"), with the bell and the notification; once it goes, it's idle until the hooks say otherwise. Declining ends the CLI. After the first hook the screen isn't read for it again.
  - taskman doesn't answer the question or trust folders for the user: that's in `~/.claude.json` and `~/.codex/config.toml`, which are the user's.
  - Seen with Claude Code 2.1.308 and Codex 0.162 on Linux (WSL), in a fresh repository under a folder neither had trusted, declining each time.
- **Claude interrupts.** Esc and ctrl+c fire no Claude hook. Once Claude has written something in the turn, an "Interrupted" line shows 115 to 270 ms after either key (7 of 7 tries, streaming or running a tool). Interrupted before it wrote anything (still thinking), Claude prints no such line: the message goes back into the input. So after either key on a working session, taskman counts the screen's "Interrupted" lines (`Session::screen_count`) and takes a new one as "your turn"; an old line from an earlier interrupt doesn't count. Failing that, 2 s of quiet within `ESC_WINDOW` (5 s) means it stopped. Both keys interrupt even with text typed in the input. The footer's "esc to interrupt" isn't used: it also disappears while the user types during a turn.
- **Quiet work (`SILENT_STOP`).** A "working" session with no output and no hook event for 8 s counts as stopped, for whatever ends without a hook. The longest gaps between draws of a working CLI, all well under it:

  | Case | Claude | Codex |
  |---|---|---|
  | A 30 s command, approved | 1.35 s | 0.66 s |
  | 60 s network stall (proxy holding the traffic) | 1.43 s ("Waiting for API response · will retry") | 0.57 s |
  | `/compact` | 0.23 s | not tried |
  | A subagent (Claude runs it in the background: Stop fires, then a new turn when it ends) | 1.65 s | not tried |
  | A permission prompt waiting (state "needs you") | silent | one draw a second |
  | Idle | silent | silent |

  So the rule can't end a working turn in these cases, for either CLI. Codex reports its interrupts and questions with hooks, so for Codex it only covers a turn that ends without Stop. A stub that sleeps without drawing does flip after 8 s; no real CLI case was found that does.

PostToolUse also writes refresh signal files when Claude uses a tracker tool or pushes / runs `gh`, so the panels refresh within a second of Claude changing what they show.

## Sessions are named, and agents use Claude Code's own messaging

Every session gets `--name`: the ticket key (`ENG-52`) or `<project>-<agent>`, qualified as `<project>/<KEY>` while another project has the same key (see the next section). Claude Code sessions on one machine can list and message each other by name (ListAgents / SendMessage), with queueing, idle notifications and per-session permission rules built in. So orchestration needed no bridge of our own: a project agent's startup brief lists the ticket sessions, and it messages them directly. A custom `taskman send` command was considered and dropped; it would have needed its own safety rules, which Claude Code already applies.

Only running sessions can be messaged, so while a project's agent runs, taskman also starts that project's ticket sessions (one per tick). Ticket sessions otherwise start lazily, when first selected, to keep memory down, and one nobody has looked at for a while is put to sleep (see "Sleeping sessions").

## Agents hand file changes to ticket sessions

A project agent runs in the project's main checkout, and once a design talk turns concrete it tends to start editing there: a change with no ticket, no worktree of its own and no PR, beside ticket sessions working on the same code. Describing the agent's job ("conversation and coordinating") didn't stop that, so in a project with a tracker the brief sets a rule: work that changes code or files goes to a ticket session, which the agent creates, adds and briefs (`file_changes` in src/app/launch.rs). Without a tracker there are no ticket sessions, so the rule isn't there and the agent does the work itself.

- **It yields to the user and the role.** A rule in the system prompt weighs heavily, and some changes don't merit a ticket: a typo, a one-line doc fix the user asks for while talking. So the user asking for the change in the agent's session overrides it, and so does the agent's role, the user's way to set it per agent ("you may edit docs directly") without a setting of its own.
- **taskman creates the ticket,** on every tracker (`taskman add --new`; see "Agents create tickets with the project's account"), so the rule is one line for all of them. Pointing agents at their own tracker tools failed the same way reading tickets did: they may be missing, and an MCP server is signed in to one workspace for every session on the machine.

## A ticket is its project and its key

A key is unique only within its project: every Local files board can have `WP-1`, and Jira, Linear and GitHub Issues keys repeat across sites, workspaces and repositories. So a ticket is identified by its project's main checkout and its key (`Ticket::is`) everywhere: lookups, background results (`Msg` carries both), `taskman add` ("already open" means in that project), the inbox (requests already named the project), and status files. The main checkout, not the project's name, because the name can change while sessions run and the folder can't. For the same reason an agent is found by its project and its name (`Ticket::is_agent`), not by `<project>-<name>` made again from the project's name: the key is made once, when the agent is added (`store::agent_key`), and renaming the project rewrites no keys, since the key is also the session's name, its status file and its owner lock. Made again, it missed every agent added before a rename: `taskman close --agent` said the agent wasn't open, and `taskman add --agent` asked for a second one with a conversation of its own. A new agent whose key an older agent already has (agent `web-x` of `acme` and agent `x` of `acme-web`) is refused, so pick another name.

- **Session names stay the key when they can.** Most users never repeat a key, and the briefs, their agents' habits and the user's own messages all use `ENG-52`. Only while another project has the same key does a session start as `<project>/<KEY>` (`store::session_name`; Claude Code accepts a `/` in names, and ListAgents and SendMessage address it as is). Different project names can slug alike ("alpha web" and "alpha-web"), and then the name also takes the start of the folder's hash: `alpha-web-3f2a/WP-1`. From the folder, so it's the same at every start; only then, so most qualified names stay readable. The name is decided as the session starts, so one started before the duplicate keeps the plain key until it restarts, and none is renamed under an agent that's messaging it. A name a running session has is never given again (one can be left from before its project was renamed): the next longer form is. The TUI knows which sessions run in its panes; `taskman status` and `taskman resume` count a session while a process holds its owner lock (`resume::runs`), as a record can still say "working" after its CLI was killed before the end hook ran. Each status record carries the session's name (`TASKMAN_SESSION_NAME`), so `taskman status` reports the name a running session really has, and the agents' brief lists it next to the key when they differ.
- **Status files go in a folder per project:** `status/<folder>-<hash>/<KEY>.json`, the folder's name for whoever looks and a hash of its whole path because two projects' folders can share a name. The hook still writes wherever `TASKMAN_STATUS_FILE` says, so where the files live is the TUI's choice alone.
- **The old layout is read during the transition.** Older versions wrote `status/<KEY>.json`. After a background update, the old TUI's sessions keep writing there, and the new `taskman status` they run falls back to it for a key that only one project has (an old TUI can't have had two). At the next start the TUI takes each ticket's latest session id from whatever files the last run left, either layout, before deleting them, so a conversation that changed after the last save still resumes; an old-layout file for a key two projects now share is deleted without being taken. tickets.json needed no change: tickets always stored their project's folder.
- **Commands know which ticket a session is:** `TASKMAN_TICKET` has the key and `TASKMAN_REPO` the project's folder (`store::session_ticket`). A session an older taskman started has only the key, which still counts while one project has it.
- **The project asked about decides whose ticket a key is.** `taskman status WP-1 --project beta` shows beta's WP-1, fetched from beta's tracker when taskman doesn't have it open, never another project's that is open: a session acts on what it prints. In a session or a project's folder, that project's ticket likewise, with two exceptions: a key with another project's prefix (`OPS-3` asked in `acme`), and a key another project has open on the same Jira site or Linear workspace, where it names the same issue and that project has the worktree and PR. Only outside any project is a key open in several projects an error naming them. A session taskman started keeps to its own project, with neither exception (see "What a session can do without a prompt" under "Untrusted text").

## Codex is a second CLI, run the same way

A ticket or agent can run OpenAI's Codex CLI instead (`Ticket::cli`). It's the same design: the real `codex` in the PTY, with hooks reporting status. Codex's hooks use Claude Code's event names and nearly its payload, so `taskman hook` serves both; `PermissionRequest` maps to "needs you", PreToolUse of `request_user_input` (its questions) too, and Codex's `Interrupt` hook to stopped (Codex has no `Notification`).

- **Hooks and trust.** The hooks are passed with `-c`, like `--settings` for Claude. Codex skips hooks it hasn't trusted, and trust is a `hooks.state` entry holding the hook's hash, which Codex also reads from `-c`. So taskman computes the hashes itself (`hook::codex_config`, following Codex's `hook_key` and `hook_hash`) and passes them along. The alternatives were worse: `--dangerously-bypass-hook-trust` also runs any of the user's own untrusted hooks, and writing trust into `~/.codex/config.toml` edits the user's settings. If Codex changes its hash, the hooks stop running and the sidebar no longer follows the session; the unit test pins the formula.
- **No shared server.** `-c` makes Codex run on its own instead of on its shared background server. That's wanted: a session whose feature flags differ from the running server's asks to restart it, which can interrupt the user's other Codex sessions.
- **The brief** goes in `-c developer_instructions`; resuming is `codex resume <id>`, checked against `~/.codex/sessions/YYYY/MM/DD/rollout-…-<id>.jsonl`.
- **Messaging stays within Claude.** Codex has no ListAgents or SendMessage. `codex queue --thread <id>` can deliver a turn to a running Codex session (tested), but it's a shell command with no session list and no idle notification, and Codex's sandbox blocks it until approved. So the rule is simple: agents only message Claude sessions, Codex sessions work alone, and the Add form says so the first time Codex is picked. A Claude agent's auto-start skips Codex tickets.

## taskman hosts the CLIs; workflows are plugins inside them

taskman runs Claude Code and Codex and nothing else. How a team works (its skills, plugins, slash commands, its own planning or review steps) lives inside the sessions, in the CLIs' own configuration, and taskman never looks at it. What taskman knows about the work comes only from the tracker, git and `gh`: the issue, the worktrees and branches, the PR. So it never needs to know a workflow, and any workflow works the same way. A workflow that differs from taskman's defaults is met with a generic setting, not by detecting it: one that makes its own worktrees sets "Don't create" for its project, and its branches are found as long as they end in `/<KEY>`.

## Integrations are optional: a folder, then what's connected

A project starts as a folder and its sessions; each integration adds a layer, per project, with no global mode:

| The project has | It gets |
|---|---|
| a folder (a git repository or not) | agents |
| + a tracker | tickets, each in its own worktree when the folder is a git repository |
| + a GitHub remote and `gh` logged in | the PR panel on its tickets |

- **Tickets need a tracker.** A ticket is a unit of work with an end: an issue, a branch, a PR, closing it removes its worktree. Without a tracker there's nothing to name that unit, and named tickets (`login-fix`) were considered and dropped: they needed their own parsing, collision rules across projects and exact branch matching, and only duplicated what an agent is. So a project without a tracker has agents only, which run in the folder and need no git. The way to get tickets without Jira or Linear is the Local files or GitHub Issues tracker (below), not a second kind of ticket.
- **Worktrees follow tickets, not git or GitHub.** A worktree exists so parallel ticket sessions don't share files or a checked-out branch; an agent is a standing session with no end, so it stays in the folder. `gh` only adds the PR panel.
- **Panels show what's connected, never a placeholder.** The tracker panel shows when the project has a tracker, the PR panel when GitHub is ready (below); one takes the column's full height, and with neither Claude gets the width. An agent's board shows once its project has a tracker or tickets. `j` and `g` still hide a panel, and say why when one turned on can't show. The Settings page says what's missing instead.
- **GitHub readiness is checked locally** (`github::probe`): the folder's `git remote -v` hosts, then `gh auth token --hostname` for them, which reads gh's own login without the network. A host with "github" in its name that gh doesn't know (an SSH alias like `github.com-work`) is checked as `github.com`, which is what gh resolves it to. gh can take a second to answer, so it's asked once per host however many projects share it, all hosts at once, on a thread. Each folder's last answer is saved with the UI state in tickets.json (`ui.github`), and the first frame draws from it, so the layout doesn't jump and the start doesn't wait for gh; the check runs at start and the panel changes only if the answer did. A folder never checked draws without the PR panel until its answer comes (its PR is fetched meanwhile, as an unchecked folder counts as ready for that). An answer this build can't read, saved by a newer one, is dropped rather than refused. The check runs again in the background on `ctrl+a r` and when Settings opens. A PR fetch failing with "gh isn't installed", "isn't logged in" or no GitHub remote also updates it, so a logout hides the panel at the next fetch.
- **Plain folders:** a path that isn't in a git repository becomes the project's folder as it is. Tickets there (with a tracker) run in the folder, with no worktree and no PR panel.

## Trackers: accounts are credentials, projects pick one

A project with a tracker has its provider, site and ticket prefix, and the account it uses. Accounts store where the token comes from (`env:VAR`, `cmd:COMMAND` or `keychain:NAME`), never the token; tokens are kept in memory only. The account form refuses any other value before it tests or saves, for every provider: "press Enter again to save anyway" is for a connection that failed, and must not become a way to save a pasted token. Each source is read once, in the background, and read again only when it failed (`ctrl+a r` retries too) or when its account is saved, so a password manager isn't asked on every change to another account or project. A ticket's tracker panel waits on its token rather than failing, and a worktree being created waits for it too, since the branch name needs the title.

- **Jira:** an Atlassian API token belongs to the person and works on every site they can reach, so one Jira account can serve any number of Jira projects (`Config::account_for` falls back to the only Jira account).
- **Linear:** a personal API key belongs to one workspace. A Linear project only picks an account for its own workspace, and saving an account checks the key's workspace, so a project can never silently use another workspace's key.

### Tokens in the keychain

A new user on macOS shouldn't have to learn `security` or shell startup files to connect Jira, so the account form takes the token itself where the OS has a keychain, puts it there, and saves where to read it back. The rule stays: no token in taskman's files.

- **A `keychain:` source, not the equivalent `cmd:` line.** `keychain:jira-1` reads plainly where `cmd:security find-generic-password -s taskman -a jira-1 -w` reads as jargon, in the form and in the pickers (`you@example.com · keychain`). It's the same on macOS and Linux, so config.json doesn't depend on which program reads it. taskman knows the item is its own, so it can replace it and offer to delete it with the account without parsing a command, and reading it runs the program directly rather than through `sh`. The cost: a version before this one doesn't know the source and treats it as a token saved by mistake, saying to change it; it neither shows nor sends anything.
- **Naming:** service `taskman`, account the account's id (`jira-1`, `linear-2`), which `next_id` gives a new account before it's saved. An id is letters, digits and `-`, so nothing needs quoting. A new account whose id an old, deleted one had replaces that item, as it should.
- **The token never goes on a command line**, where `ps` shows it to other users. `secret-tool store` reads the secret from stdin when stdin isn't a terminal. `security add-generic-password -w` with no value asks on the terminal, which `proc::run` doesn't give it; so taskman runs `security -i` and writes the whole command to its stdin, the token double-quoted. A token must be printable ASCII without spaces (Jira's and Linear's are), checked before anything runs, so it can't break that line. `-U` and `secret-tool store` both replace an item that's there.
- **Read back to check.** `security -i` may exit 0 when the command it read failed, so a save counts only once the same item reads back as the token written. The form's check does this before it tests the connection, on a thread through `proc::run` with the 60 s limit of a `cmd:` (time to unlock the keychain in its own window). A save that fails offers no "save anyway": that would save an account whose token isn't anywhere.
- **The form forgets the token** once it's written: the field is cleared and the form remembers only the source (`Form::stored`), so an "Enter again to save anyway" after a failed test saves without it. It's typed into a field drawn as dots.
- **Offered only where it works** (`Keychain::probe`, on a thread at start): `security default-keychain` answers on macOS; on Linux `secret-tool lookup` of an item that isn't there exits 1 silently when a Secret Service answers, and says why on stderr when there's none (WSL, a server, no D-Bus session). Neither opens a window. Where there's none, the form offers a private file instead (below). Until the check answers, a form shows only Read from, as it did before there was File: offering File then would let a quick save put a token in a file on a machine that has a keychain. A form open when the answer comes offers what was found, its default and note with it, unless a source was typed in Read from meanwhile (`keychain_probed`).
- **No pre-filled source.** v0.1.0 opened the form with `env:JIRA_API_TOKEN` filled in, which read as already done. Now the form starts on the keychain, or a file; picking Variable or command fills in the suggested variable (a second Linear workspace's own), which the user then has to set.

### Tokens in a private file

Without a keychain (WSL, a server), the form used to offer only a variable or a command. A variable set in another terminal isn't in the one taskman started from, so setting one means a new terminal and a restart, and the variable ends up in plain text in a startup file and in every process's environment, every session's included. `gh`, the AWS CLI and npm keep a token in a file only the user can read where there's no keyring; taskman does the same, as **File** under Keep in, offered and the default only where there's no keychain (where there is one, the keychain is better and the choices stay Keychain or Variable or command).

- **A `cmd:cat` source, not a new kind.** The account saves `cmd:cat '<path>'`, so config.json still says only where to read a token, every version of taskman reads it, and nothing else in the code learns a new source. The path is single-quoted for `sh`, a `'` in it escaped. The form recognises its own command (`token_file::name_of`) to show File and replace the token in place.
- **Private from creation.** The folder `tokens/` beside config.json is made 0700 (`DirBuilder::mode`) and each file 0600 (`OpenOptions::mode`, `create_new`, `O_NOFOLLOW`): never readable by others even for a moment, whatever the umask, and never written through a link. The token goes to a temporary file in the same folder that's synced and renamed over the old one, so a crash leaves the old token or the new one. A folder that isn't one, isn't the user's or lets others in is refused with the fix (`chmod 700 …`), as is a link or a folder where the file goes.
- **Safer than a variable, no safer than the user.** The token isn't in any process's environment and is in no startup file, but a session runs as the user and could `cat` the file, as it could run any `cmd:` or read the keychain item.
- **Not deleted with the account.** Deleting an account leaves its file; the guide says where it is and how to remove it. Recognising the file from the command is enough to offer that later.

### Sign in first, then pick the project or team

The project form used to ask for the ticket prefix before taskman had connected, then send a new user to a second form for the account, asking the provider and site again. The prefix is the Jira project or Linear team key, which a new user may not know, and which the tracker can tell once the account can sign in. So the form asks in the order the answers become knowable: tracker, site or workspace, the account (a new one's fields inline, in the same form), then the prefix, picked from a list.

- **One form, the account inline.** The account's fields are the account form's (`new_account_fields`, `account_rows`), and saving runs the same pieces (`draft_account`, `check_account`, `account_verdict`, `keep_account`): keychain save with read-back, the unset-variable and failed-command messages, the connection test and "save anyway" don't drift between the two. The project and its account are saved together, only once the test passes or is waved through, so a cancelled form leaves no account behind. Accounts in Settings stay for editing or deleting one on its own.
- **Listed when focus leaves the sign-in, not on Enter.** Enter means save in every taskman form; making it mean "connect" here would make it mean two things in one form. The list is asked for once the sign-in is complete and focus is off the fields it's typed in (`SIGN_IN_FIELDS`), so not on every key: in practice when Tab leaves the token for the field the list fills, or at once when a saved account is picked, or when a project's settings are opened for editing. Any change to the sign-in drops the list. A pasted token is used from memory for the listing, and reaches the keychain only on Enter, as in the account form, so a form abandoned before then leaves nothing there.
- **A list to narrow, not ←/→.** A Jira site can have dozens of projects; cycling them with ←/→ would be slow and hides their names. The field is text with the account's projects or teams listed under it while it's focused, narrowed by key or name and picked with ↑/↓, as the Add form's open issues are. ↑/↓ past the list's ends move to the fields around it, as a search box's dropdown does, and Tab always does; leaving takes only an entry highlighted. The only match is picked on Enter; typing a key the list doesn't have is kept, for when the list can't load (no permission to list projects, network down), and saving asks once to confirm a key the list doesn't have.
- **Each difference is a method** (`Provider::prefix_field`, `site_field`, `lists_choices`, `signs_in_with_email`; `Client::choices`, `Tracker::suggested_prefix`). Jira's `project/search` and Linear's `teams` are paged (`CHOICE_PAGES` pages at most) and sorted by key; a key that couldn't be a prefix is left out. Names are tracker text, printed through `untrusted` and never put in a brief.
- **No format change.** A project still saves its tracker, site, prefix and account; the list isn't saved, it's asked for again.

The ticket prefix is only a typing shortcut (`52` becomes `ENG-52`); tickets are always fetched by their full key. A project's tracker is set in its settings; taskman doesn't read it from files in the repository (see the roadmap for settings committed there).

## Local files: the board lives in the project folder

A project's tracker can be markdown files in a folder of the project (`workplan/`, src/local.rs), so a project gets tickets, a tracker panel and worktrees with no account. The subfolder a file is in is its column; the file is `<KEY>-<slug>.md`, and parsing it gives the same `tracker::Issue` the panel and `taskman status` already show. It is a third provider beside Jira and Linear, not a second kind of ticket, so everything else (sessions, worktrees, PRs, `taskman add`) works unchanged.

- **One board, in the project folder.** If `workplan/` is committed, every worktree has its own copy, which goes stale as tickets move. Reading or writing those copies would give each session a different board, so taskman uses only the project folder's (`Tracker::board` takes the project's main checkout, never a worktree): the panel, `taskman status`, `taskman move` and `taskman add --new` all do, from wherever they run. They find the project the way `taskman add` does (the session, `--project`, the folder, whose worktrees `git worktree list` maps to the main checkout), and the briefs say a worktree's copy isn't the board.
- **Its folder is saved twice.** `Tracker::folder` holds it, and tickets.json writes it to `site` as well, where builds before `folder` kept it and still read it (`store::SavedTracker`). An older build beside a newer one, a debug build or one auto-update behind, then finds the same board instead of treating the project folder as one. A Local tracker saved without `folder` is read from `site`.
- **taskman never commits it.** Committing `workplan/` makes a shared board whose moves show up as changes on main; ignoring it makes a private one. Both are reasonable, so it's the user's call, and taskman only renames and writes files.
- **The key is in the file name, the title in the file.** Names like `WP-3-fix-login.md` keep keys stable through renames of the title, and the name gives the branch, as Linear's `branchName` does, so the `{tracker}` branch format works: the key and the rest made a slug (`worktree::slug`, the name `taskman add --new` gives a file), not the name as it is, as whoever committed the file chose it (see "Untrusted text"). A new ticket takes the highest number in any column plus one, so a number is never reused while its file exists; a lock in the state folder (not the board, which may be committed) keeps two creates at once apart.
- **Checked on every poll, no refresh timers,** so a file moved by hand shows within a poll. The poll runs on the UI thread every 300 ms, so it mostly only reads modification times: a board is listed again only when one of its folders' times changed (a file added, removed or renamed in it), and a ticket's file is parsed again only when its own changed. Folder times tick on a coarse clock, so a listing taken within 2 s of a folder's change isn't trusted and is redone (`local::Cache`). The Add form uses the same cache on every keystroke.
- **`taskman move` writes the file itself,** unlike `taskman add`: the TUI doesn't hold the board in memory, it reads it, so there's nothing to overwrite and no inbox is needed. `taskman add --new` from a shell creates the file first and then sends the usual request with the new key; from a session the TUI creates it once the user approves. The other trackers' tickets are created the same way (see "Agents create tickets with the project's account").
- **The open key edits the file.** `ctrl+a o` gives the terminal to `$VISUAL` or `$EDITOR` (vi if neither) until it exits; the sessions keep running meanwhile.
- **Codex's sandbox** lets a session write only its own folder, and the board is outside a worktree, so a Codex brief asks to run `taskman move` outside the sandbox.

## GitHub Issues: the repository's issues, through gh

A project can take its tickets from its GitHub repository's issues (src/github_issues.rs). It is a fourth provider, not a mode of the PR panel, so sessions, worktrees, `taskman add`, `close` and `status` work as for the others.

- **Keys are `<PREFIX>-<number>`** (`WEB-12` for issue #12), the prefix being the project's ticket prefix, which defaults to one from the repository's name. GitHub's own `#12` doesn't fit where keys go: the shell reads `taskman add #12` as a comment and passes nothing; status and owner files make `#` an `_`; and every repository has a #12, so names would collide across projects all the time and sessions would mostly be `<project>/#12`. `acme/web#12` has a `/`, which session names already use for `<project>/<KEY>`, and can't be a folder name. `<repo>-12` breaks on the dashes and dots repository names have (a key is letters, digits and `_`, a dash, then the number) and makes long branch and session names. A fixed `GH-12` works, but every GitHub project would share it. `PREFIX-N` is the shape Jira and Linear keys have, so `Ticket::is`, `store::session_name`, the branch formats, `github::mentions`, the inbox and `taskman add 12` take it unchanged. The tracker reads GitHub's ways of writing an issue as input (`#12`, `acme/web#12`, the issue's link, `Tracker::key_from_input`), and refuses a pull request's link or an issue of another repository, so they never become a dead ticket.
- **No account and no token: `gh` is asked,** as the PR panel asks it, on its own login. People who have it set up already need nothing more, and taskman stores nothing. The cost is gh's model of accounts: one active account per host, so someone with work and personal accounts may have the other active; access errors name the repository and host and say to run `gh auth switch`, or `gh auth refresh -s repo` for private repositories, rather than "not found".
- **The repository is saved with the project** (`Tracker::site`, `acme/web`, or `host/acme/web` off github.com), read from the remotes as gh would pick them (`github::default_repo`) when the project is saved, not typed. Every call names it (`gh api graphql` with owner, name and `--hostname`), so a worktree whose origin is a fork, or a folder whose remotes changed since, still reads the project's issues, and the issue's URL, the panel and `taskman status` agree. A project without a GitHub remote can't save this tracker.
- **GraphQL, one call per issue:** the title, state and its reason, labels, assignees, body, the newest 100 comments with their total, and the PRs that close the issue (`closedByPullRequestsReferences`), through `issueOrPullRequest` so a number that is a PR is told apart from one that doesn't exist. Both are "not found" to `taskman add`, which then refuses the key.
- **The PR panel prefers the PR that closes the issue.** GitHub links PRs to the issues they close ("Fixes #12", or by hand in the sidebar), which is a better signal than a branch name or a title mentioning the key. So the lookup asks for those first (`Tracker::closes`) and shows the newest open, else merged, one in the issue's repository (viewed there with `--repo`); with none, it falls back to the branch and key search. That query failing is only a fallback too: the search's own calls say what's wrong.
- **The Add form lists open issues,** the newest 100 by update, those assigned to gh's account first, fetched in the background when the form opens on the project (again after a minute) and filtered as you type: digits by number, words by title, Enter adding the one match. A closed issue is still added by its number: reopening work or reviewing a closed one is legitimate. Jira, Linear and Local files list theirs the same way (see "The Add form's open issues").
- **Tests run no gh.** The client takes its runner, which tests replace with recorded output from `tests/fixtures/github/`; a unit test that reaches the real runner gets an error instead of running gh.

## The Add form's open issues

- **Every tracker lists them, through one shape** (`tracker::Listed`: the ticket key, title, whether it's yours), so the form's matching, picking and drawing don't depend on the tracker. `Client::open_issues` puts yours first and drops a key that doesn't read as one (letters, digits or `_`, a dash, a number): a key names a worktree folder and a branch, and it comes from the tracker. Titles are printed through `untrusted`. GitHub's issues carry the project's prefix in their keys (`WEB-12`) and are shown the GitHub way (`#12`, `Provider::written_key`).
- **Jira and Linear find them by the ticket prefix,** the project or team key it names, so a project without a prefix lists nothing (`Tracker::lists_open`). Linear: one GraphQL query, the team's issues whose state type isn't completed or canceled, newest updated first, with the viewer's id to mark yours. Jira: `myself` for the account's id, then one `search/jql` call (`statusCategory != Done ORDER BY updated DESC`); a search can't sort the current user's issues first, and the 100 most recent are the same either way.
- **A Local files board is read from the disk, every time the form opens** (no network, so no minute's wait): the tickets in columns not done, done being what the panel colours as done (`local::category`), or the last column on a board with no such column. Nothing is yours: a frontmatter assignee is free text, and taskman has no name of yours for a board to compare it with.
- **On a board, a title is still a new ticket.** Typed words narrow the list but don't pick a match as on the other trackers, since `n` with a title is how a board's tickets are made; ↑/↓ and Enter add an existing one.
- **↑/↓ pick from the list only while the Ticket field has issues listed;** otherwise they move between fields, as in every form. Past the list's ends they move between fields too, as a search box's dropdown does (`List::step`): ↑ from the first issue goes back to what's typed, then to the field above, and ↓ past the last to the field below, dropping the highlight so leaving picks nothing, but never round from the last field to the first. Stopping at the ends trapped the arrows in the field. Tab always moves. The Ticket field (an agent's Name) is the form's last, its list at the bottom: with a hundred issues, ↓ to the end of the list was no way out to CLI, Worktree and Base, and with Ticket last nothing is below it to reach. The form opens on Type, set to Agent, so one ←/→ makes it a ticket. What's typed on Type, or on any of the form's choices, goes to the Ticket or Name field, at its cursor (`add_form::focus_text`): a choice has nothing to do with a letter, and dropping it lost the first thing typed with no sign why. A number, a link or a key with the project's prefix typed or pasted as a name switches Type to Ticket, keeping the text (`names_ticket`), so `52` adds ENG-52; another key stays a name, since `phase-2` reads as a key and is a fair one. Only typing into the name switches it, not every change, or ←/→ back to Agent would be undone at once. Settings' forms keep dropping it: they have several text fields, and no one is the field meant. The highlight is an index into the matches, dropped when any value changes (`Form::edited`) or a new list arrives, so it can't land on an issue the input no longer matches. The window keeps `OPEN_ISSUES_SHOWN` issues and moves only when the highlight leaves it; the line under it counts those above and below.
- **A late list is dropped** unless its folder still waits on that request and the project's tracker is the one asked, prefix and board folder included (`add_form::Listing`).
- **Unit tests reach no tracker:** Jira's and Linear's clients refuse any address but `replay`'s local server under `cfg(test)`, as GitHub's refuses to run gh, since the mock project's Linear client would otherwise be asked whenever a test opens the Add form.

## Sessions read their ticket through `taskman status`

A session's brief carries only the ticket's key and URL, written once at start. To read the ticket it needed its own tracker tools, which may be missing (Codex usually) or signed in to another workspace (a Linear MCP server is signed in to one workspace for every session on the machine). taskman already holds the right account per project, so `taskman status` (src/status.rs) reads the ticket and its PR with it and the briefs point there.

- **A command, not an MCP server per session.** Passing each session a tracker MCP server with the project's token would also let sessions write to the tracker, but depends on Linear's and Atlassian's hosted servers accepting tokens that way (unverified), and wouldn't include the PR or the agents' overview. It stays an idea in the roadmap; the two can coexist.
- **Fetched fresh, not from the TUI.** The TUI's data lives in its memory, and the command must work from any shell. It reuses the same pieces: `Config::account_for`, `Account::resolve_token`, the tracker clients (`tracker::Client::for_project`), `github::find_worktree` and `github::fetch`. Linear text stays Markdown (`tracker::Text::Markdown`): the panel's plain text drops link targets and code marks.
- **The binary, by name.** The briefs say `taskman status`, and Claude's permission rule matches that text (`Bash(taskman status:*)`, in taskman's `--settings`, so the user's settings stay untouched). taskman may not be on PATH, or another build may be (a debug build running beside an installed one), so each session gets `~/.local/state/taskman/bin` first on its PATH, holding only a `taskman` link to the running binary. Putting the binary's own folder first instead would also reorder whatever else lives there (`~/.cargo/bin`, say). Only one taskman runs per state folder (see "Saved state is never replaced by less"), so the link is always the running one's.
- **Agents get the project.** An agent's `TASKMAN_TICKET` is its key, `<project>-<agent>`, so with no key the command lists the project's tickets with their session state, read from the hooks' status files. That keeps an agent current without interrupting the ticket sessions.
- **From a shell, the folder decides.** Outside sessions there is no `TASKMAN_TICKET`, but the folder says what the user is looking at. A ticket's saved folder is where its session started, often the main checkout because the worktree came later, so the worktree is also found by its branch, like the PR lookup does. The main checkout always means the project, and the deepest worktree wins when they nest. Folders are compared with symlinks resolved.
- **All the feedback, or says what's missing.** Sessions act on what it prints, so a review that says "changes requested" without its text, or a comment list cut short without saying so, means instructions missed. The PR's details query (`github::view`) fetches every review and comment, the newest 100 of each and then a query per older hundred, as `gh pr view` paged through them, and keeps review bodies. The same query has the inline review threads, the newest 100, each with its first comment and newest 20 replies, and `taskman status` prints the unresolved ones with file and line. Trackers give the newest 100 comments: Jira's issue holds only its oldest, so past them the comment endpoint is asked for the newest; Linear has no count, so the older pages are counted by id. Whatever was left out is counted and said, in the text and in `--json` (`comments_left_out`, `left_out`, `replies_left_out`). A reply without the threads is shown as such (`review_threads_error`), not as no threads, and still shows the PR; a query that fails as a whole fails the PR with it, since the threads come in the same query. The text shows the review text that still stands (none of its author's approvals or change requests came after it), and `--json` every review.
- **Codex's sandbox blocks network access,** and the narrowest way past it is Codex's own: approving the command, or a `prefix_rule` the user adds by answering "don't ask again" (Codex writes it to `~/.codex/rules`). `sandbox_workspace_write.network_access=true` would open the network to every command in the session. The Codex brief asks to run it outside the sandbox, so the first try isn't wasted. Codex sets `CODEX_SANDBOX_NETWORK_DISABLED=1` even for an approved command running outside the sandbox, so the variable only adds a hint to a failed request; it can't decide whether to try.

## Agents create tickets with the project's account

For the reason `taskman status` reads tickets with the project's account (the session's own tracker tools may be missing or signed in elsewhere), `taskman add --new TITLE` creates them with it: in Linear's team or Jira's project the prefix names, in the GitHub repository, or on the board (`Client::create`). From your own shell it prints the new key and its link, then sends the usual inbox request; from a session the TUI creates it once you approve (see "From a session, the user approves the ticket first").

- **On the command's side from a shell, in the TUI from a session.** The command already reads the token and asks the tracker (it checks every key it adds), as `taskman status` does, so from your own shell it creates the ticket itself, which works while taskman is closed. A session's ticket waits for you in the TUI's dialog instead, so the TUI creates it: an `Item::New` in the request (inbox format 5), created on a thread with the TUI's client once you press Enter (`App::answer_new`, then `Msg::Created`), then added through the same code as any key. The command waits up to a minute for your answer (`add::ASK_WAIT`, short of Claude Code's two minutes for a command), so the session hears the key, or that you declined, in the same call; past that it says you haven't answered, and the dialog still creates and adds the ticket if you approve later. Codex loses nothing: `taskman add` runs outside its sandbox anyway, to write the inbox.
- **Never retried.** An agent that sees a failure tends to run the command again, so a create that may have reached the tracker (a timeout, a broken connection, a server error, an answer without a key) says the ticket may exist and to look before running it again (`tracker::maybe_created`); one that clearly didn't (no connection, refused with a reason) just says why. ureq doesn't retry a POST, `net::retry_dropped` asks only reads again (Jira's GETs and Linear's queries, not the mutation), and `gh api` retries nothing. Tickets already created are printed as they're made, and if the inbox request then can't be written, the command names them to add by key, so none is left in the tracker unknown to taskman.
- **Jira: a Task, or a clear refusal.** The project's issue types come with the project (`project/{key}`): Task, else its first standard type, as a project's default type isn't visible to an ordinary account. Required fields aren't looked up beforehand (`createmeta` is a page per type, and Jira checks anyway): the create's 400 names them, and the command says the project requires fields taskman doesn't fill, so the ticket is made in Jira and added by key. Linear omits the state, so the team's default applies. GitHub's is the REST call through `gh api`, since GraphQL's `createIssue` needs the repository's id first.
- **From a session, the user approves the ticket first.** `taskman add` is on the sessions' allow-list (see "`taskman add` goes through an inbox, not `tickets.json`"), and Claude's rules match a prefix, so one can't let keys through and stop `--new`. Junk tickets alone would be acceptable, as the user sees and deletes them. But the title and description are free text the session chooses, published under the user's account: a session talked into it by text it read (see "Untrusted text"), such as an issue a stranger wrote on a public repository, can put a secret in them, from the working tree (Claude reads files in the project without asking) or from its context, and so publish it as a public issue, or in a shared Jira or Linear, where Claude would otherwise ask before any write to the network (`curl`, `gh issue create`). So when `TASKMAN_REPO` is set (the command runs in a session), `--new` doesn't create the ticket: it asks the TUI, which shows who asked and each title and description in full, behind the quote bar that marks text taskman didn't write and scrolling when long, and creates nothing until Enter (the dialog that approves agents, which ignores keys for its first 1.5 s). Esc creates nothing, and the command says the user declined and exits 1. From the user's own shell, `--new` still creates at once. A session can unset `TASKMAN_REPO`, but `env -u TASKMAN_REPO taskman add` doesn't match the allow-list's prefix, so Claude asks first. Considered and not chosen: refusing `--new` in a session and pointing at `env -u TASKMAN_REPO`, which prompts every time with less to see than the dialog shows; asking only for trackers strangers can read, which taskman can't tell. What comes back from the tracker (the key, checked to read as one, and the link) is printed through `untrusted`.

## Saved state is never replaced by less

The TUI rewrites `tickets.json` and `config.json` whole from memory, so whatever it failed to read it would erase at the first save: every project, ticket, session id and account.

- **Only a missing file means empty.** `store::read_json` gives the default for a file that doesn't exist and an error for anything else: unreadable, invalid JSON, or valid JSON this release can't map, such as a provider added by a newer release. Older and newer builds meet often (auto-update, a debug build beside the installed one).
- **The TUI refuses to start** on that error rather than start empty with saves blocked: a toast is easy to miss, and work done in a session that can't save is lost at quit. The file is left where it is, not renamed, so the newer build that wrote it still finds it. The CLI commands fail with the same message instead of seeing no projects. The message is printed before the alternate screen so it stays on the terminal.
- **Missing fields aren't errors** where a default makes sense: optional fields have `#[serde(default)]`, and so does all of `UiPrefs`. A new field needs one too, or files saved before it stop loading. Fields with no sensible default (a ticket's key, a project's folder) stay required.
- **Fields a build doesn't know are kept.** Every struct in the two files has a `#[serde(flatten)] extra` (`store::Extra`) that holds what it didn't recognise and writes it back, so a field a newer release added survives a save by an older one: running an older binary once by accident (a debug build from an old branch, a second install earlier on `PATH`) used to drop such fields, and `"sleep_after": null` (never sleep) lost that way made sessions sleep after an hour. Code that rebuilds a saved struct rather than editing it, like the project and account forms, carries its `extra` over. Floats in them come back exactly (serde_json's `float_roundtrip`). Builds before this keep nothing, so it protects only from here on.
- **A format number for changes older builds would misread.** Both files start with `"format": 1`; a file without one is format 1. `read_json` refuses a file of a newer format, before reading anything else in it, with the same "run the newer taskman" message, and leaves it as it is, as Cargo does with `Cargo.lock`'s `version`. A new field, kept by older builds and defaulted when missing, doesn't raise the format, so older and newer patch releases share the files. Raising it (`store::FORMAT`) is for a change in meaning, such as a field that now says something else, and makes a breaking release; the build that raises it reads the older formats and writes its own.
- **One TUI per state folder.** Two would each save their own copy, the last undoing the other's changes, and each clears the status files at start. The TUI holds an `flock` on `lock` in the state folder, which the system releases however the process ends, so there's no stale pid file to clear. Releases from before the lock don't take it, so a fresh `inbox/alive` also refuses, but only from one of those (0.4.8 to 0.4.15, before the public repository; `alive` says its version, and from 0.1.29 that it takes the lock): a TUI that takes the lock removes `alive` as it quits, so a file still there once the lock is had was left by one that was killed or crashed, however fresh. Trusting the heartbeat's age instead refused every start for 3 s after a kill -9, an OOM kill or a panic. The new TUI removes it and says the last one didn't quit cleanly. `alive` is also removed when `main` ends any other way (an error, a panic: `Running`'s drop, before the lock goes), so a start that fails, with no terminal say, leaves nothing that says taskman runs.
- **Failed saves stay on screen** as a toast until a save works, since later toasts would hide a single one and changes are being lost meanwhile.
- **A claim goes only once the state no longer needs it.** `taskman resume` finds sessions in the saved state, so a change that lets go of a session's owner lock, or deletes a folder a session could run in, is saved first (`App::try_save`) and undone when the save fails: renaming an agent, closing a ticket (the dialog and `taskman close`) and removing a project leave everything as it was, sessions running and claimed, and say why. Saved after the fact, as they once were, a rename whose save failed let go of the old name's lock while tickets.json still listed the agent under it, and `taskman resume` under the old name started a second CLI on the conversation (seen with v0.4.30). Other changes (preferences, a ticket added, a session id adopted) stay in memory with the toast, as nothing is let go on their account.

## `taskman add` goes through an inbox, not `tickets.json`

A ticket the planner just created took copying its key into the Add form. `taskman add` (src/add.rs) does it from any shell or session, with the project's defaults.

- **The TUI owns `tickets.json`.** It holds its own copy in memory and rewrites the file on every change, so a command editing it would be overwritten at the next save, and a lock wouldn't help. So the command leaves a request in `~/.local/state/taskman/inbox/`, the TUI adds it on its next status poll (300 ms) through the same code as the Add form (`add_ticket`, `add_agent`), and writes a reply the command waits for. A request waits for the next start when taskman isn't running.
- **Knowing whether taskman runs:** the TUI writes `inbox/alive` as soon as it holds the state folder's lock (see "One TUI per state folder"), rewrites it once a second (the inbox itself is read every 300 ms) and removes it as it quits. A command counts taskman as running while the lock is held and `alive` is there (`add::tui_running`, testing the lock shared for a moment, which a taskman starting just then waits out), or while `alive` is under 3 s old, for a release from before the lock. Otherwise it isn't running (or is quitting, or crashed), so the command doesn't wait and the request carries no reply deadline. The heartbeat's age alone isn't enough: it's the file's time on the wall clock, which can step forward by seconds against the clock the TUI keeps time with. WSL steps it by about 2.5 s every half minute or so, which made a running taskman look closed now and then: the command said "taskman isn't running", and the request was added later as if it had been. A lock needs no process checks, which differ on macOS. Requests are claimed by renaming them, so two taskmans running at once never add one twice.
- **The command checks what it can on its own:** the project (session, folder, then key prefix), the key (a bare number takes the prefix; another project's prefix is refused) and whether it's already open, so mistakes come back at once, taskman running or not. It also fetches the issue with the project's account: a key the tracker says doesn't exist (`FetchError::NotFound`, which each tracker sets where it knows: Jira's 404, Linear's missing entity, GitHub's unresolved issue, a board with no file) is refused, so an agent's typo doesn't add a dead ticket, and the title goes in the reply. If the tracker can't be asked (no account, Codex's sandbox), the key is added unchecked.
- **It doesn't take focus.** The user may be typing in another session, so the selection stays; the ticket shows `+ new` until selected (in memory only) and a toast names who added it. Sessions start as before: while a Claude agent runs, its project's Claude ticket sessions start, so it can message the new one. Nothing sends the new session a prompt, which would spend tokens the user didn't see.
- **Agents add agents, with a role, not a first message.** An orchestrator sets up helpers with `taskman add --agent tester --role "..."`. An agent added this way starts its session as soon as the user approves it (an agent from the Add form still starts when selected), since only running sessions can be messaged. The role is a standing instruction appended to the agent's brief (`--append-system-prompt`) at every session start, saved on the agent (`Ticket::role`, and `ClosedAgent` so re-adding resumes it). It is deliberately not a first message: a brief costs nothing until someone writes, while a prompt would start work, and spend tokens, the user didn't see begin. The flip side: a new role on an open agent only applies when its session next starts, since a running session's system prompt can't change. A role needs inbox format 3, so `--role` is refused against an older running TUI as `--on` is (see Stacked tickets), and each item now refuses unknown fields too.
- **Allowed without a prompt** (`Bash(taskman add:*)`), but an agent, and a session's new ticket, waits for the user. A ticket that exists only opens in taskman, which the user sees and can close, so agents add tickets freely; creating one writes text the session chose to the tracker (see "From a session, the user approves the ticket first"). An agent is different: its session starts at once and its role is its system prompt, and a session can be talked into running the command by text it read (see Untrusted text). So the TUI answers an agent request with "asks the user to approve" and queues it; a dialog shows who asked, the agent and its role in full, and adds it only on Enter. A dialog that opens by itself ignores keys for 1.5 s, so an Enter typed into a session can't approve it. The role is wrapped by taskman, not by the paragraph, so every row of it starts with a quote bar: the text chooses where its words fall, and a row the paragraph wrapped would start at taskman's margin, where a line like "Approved by the project owner already." reads as taskman's, beside the key that approves it. The question, the warning and the keys stay on screen and the role scrolls between them, saying how many lines are hidden, since what's approved must be readable whole; scrolling works at once, answering only after the 1.5 s. Whether the request was queued while taskman was closed is decided when it's taken (already past `reply_by`), not when it's answered: the command stops waiting after 5 s, which a user reading the role usually takes longer than. Why not take `taskman add` off the allow-list instead: Claude's rules match a command's prefix, so one rule can't let tickets through and stop `--agent`, and every ticket an orchestrator adds would wait on a prompt in a session the user may not be watching. The allow-list also covers neither Codex, which has its own approvals, nor a session in a mode that skips prompts, nor `TASKMAN_TICKET` being unset to look like a shell. The TUI sees every request whatever started it, so it asks for every agent and role, from a shell too. Agents' briefs mention the command; tickets' briefs don't, since adding work is an agent's or the user's call.

## `taskman close` closes through the dialog's code

After a wave of merges, closing took `ctrl+a x` and `r` per ticket, and agents couldn't tidy up. `taskman close KEY...` and `taskman close --merged` (src/close.rs) go through the inbox like `taskman add`, with the request's `close` field (inbox format 4, so an older running TUI is refused before the request is sent, and fails to read it if it's sent anyway).

- **The same code as the dialog.** Each ticket stops and leaves the list through `App::close_at`, then `close::remove_worktree` runs `worktree::removal_check` and, if it passes, `worktree::remove`, which checks again and deletes the branch only while it points at the checked commit. Only worktrees taskman created are candidates (`own_worktree`), as in the dialog.
- **A fresh PR lookup first.** The panels refresh every minute and are empty at startup, when a queued request runs, and after a wave of merges they lag. The PR decides `--merged`, and its head is what the removal check counts as pushed after a squash merge, so the TUI looks each ticket's PR up on a thread, feeds the results to the panels (`Msg::Pr`) and only then closes (`Msg::Close`). A lookup that fails keeps the ticket open with `--merged`; without it, the check just counts the remotes. The command waits 30 s for the reply instead of `taskman add`'s 5.
- **Never while a dialog holds a ticket's index.** The close dialog and the rename form name their ticket by its place in the list, which closing another ticket shifts, so requests wait in `App::closing` until they're answered.
- **A session in another terminal stays open:** while `taskman resume` holds the ticket's owner lock, closing would leave that session running in a worktree the removal could take away, so `App::close_at` refuses, for the dialog and the command alike: "quit it there first". The dialog doesn't open for such a ticket, and Enter or `r` checks again in case the session moved since.
- **The worktree stays reserved until it's removed.** The ticket leaves the list at once, but removal runs later on a thread and git can take a while; a ticket added again in that gap would find its old worktree and start a session there, and the removal would then delete the folder under it. So `App::close_at` keeps the ticket's owner lock (the pane's, or one it takes) and writes `closing <pid>` to it, and the removal thread lets go only once it's done or gave up. While it's held (`Owner::Closing`) adding the ticket, from the form or `taskman add`, starting its session and `taskman resume` are refused: "its worktree is still being removed; try again in a moment". The same lock as a hand-off rather than a second one, so there's one place that says who may run a ticket's session. The close is saved before the session stops: a close that can't be saved leaves the ticket open, since `taskman resume` would still find it, and the worktree with it. Right before deleting, `close::remove` also keeps a folder a saved ticket runs in, should another ticket have taken it.
- **The reservation outlives taskman.** A lock the TUI holds goes when it ends (a kill, a crash, the terminal closing), but the `git worktree remove` it started goes on, so a taskman started again could hand the folder to a re-added ticket just before git deletes it. That git gets its own copy of the lock's descriptor (`Hold::share`, which clears close-on-exec in that child only, as `taskman resume` does for its CLI). An `flock` belongs to the open file, not the process, on Linux and macOS alike, so the lock lasts until the last copy closes: the reservation ends when git does, whoever is left. Not `PR_SET_PDEATHSIG` (Linux only, and it would stop a half-done removal). A normal quit waits for removals still running (`App::may_quit`), saying so in the toast, so the branch goes too and `taskman close` gets its reply. It also waits while git is still creating the worktree of a ticket closed meanwhile, which is then removed, unless it was closed with `--keep-worktree`.
- **Not on the sessions' allow-list.** Adding a ticket is visible and undone with a key; closing stops a session and can remove a folder. The removal check means nothing unpushed is lost, but a session talked into it by text it read (see Untrusted text) would still end other sessions' work in progress, so Claude asks the user before running it, as Codex does. The TUI doesn't ask again: the command's own prompt is the approval, and a shell's user asked for it themselves.
- **The command finds each key's project as `taskman status` does** (`status::locate`), so a key open in two projects is refused without `--project` rather than closed in the wrong one. `--merged` alone leaves the choice of tickets to the TUI, which knows what's open right now.

## Untrusted text

On a public repository anyone can open an issue or comment on a PR, and on a shared tracker many people can write. Sessions act on what they read, so the threat is that text reaches a session as instructions (prompt injection) or reaches a terminal as escape codes. What taskman does:

- **Briefs hold no tracker text.** A brief is the session's system prompt (Codex: developer instructions), where text carries the most weight. Ticket briefs name the key and URL; agent briefs list tickets by key, worktree, branch and PR state, without titles or statuses, and tell the agent to run `taskman status`. Local files column names, folder names from the repository, are kept to one line each (`untrusted::line`). Branch names are others' text too (a Local files file name, a PR's head branch) and git takes spaces, `;`, `$()`, backticks and the characters that hide text in one, so a brief names a branch only when `untrusted::branch` passes it (ASCII letters, digits, `.`, `_`, `/`, `-`) and otherwise says to run `taskman status` for it; the sidebar, the panels and `taskman status` print branches through `untrusted::line`. A branch of plain characters can still spell words; that is accepted, as its name is short and has no spaces, and taskman makes the branch itself or takes it only from the repository's own PRs (see "Finding a ticket's PR").
- **`taskman status` quotes, cleans and labels.** Titles, descriptions, comments, reviews and PR text go through `src/untrusted.rs`: inline fields onto one line (a newline can't start a line that looks like taskman's), bodies indented as blocks, everything without C0/C1 control characters but newline and tab (OSC 52 would set the user's clipboard, OSC 8 spoof links) and without the characters that hide text from a reader (Unicode tag characters and variation selectors, which draw as nothing yet each spell out a byte a model may read; zero-width spaces, word joiners, invisible operators and the byte order mark, which draw as nothing too; bidirectional embeddings, overrides and isolates, which show text in another order than it's read in: all known ways to slip instructions past a person reviewing the text), and a note above it all saying it's data, not instructions (`note` in `--json`). Emoji need two of those: U+FE0F makes ⚠ the two-column ⚠️ (see "Emoji that terminals measure differently"), and the zero-width joiner builds 👩‍💻, as the joiner and non-joiner shape Indic and Persian letters. So each is kept only where it has that job (`untrusted::kept`): one presentation selector (U+FE0E or U+FE0F) straight after an emoji, never after a letter or another selector, and a joiner only between two visible characters outside ASCII. The other selectors go wherever they are; the supplementary ones are also how Japanese names pick a glyph, which then shows in its default form. A file or column name of a Local files board is someone's text too: `taskman status` prints the ticket's file on one line (`--json` keeps it as it is), and `taskman move` its columns and file. New tracker or PR text printed anywhere goes through the same module. `taskman add` and `taskman move` clean what they print too. The TUI needs none of this: ratatui drops control characters.
- **What a session can do without a prompt** is read (`status`), move a Local files ticket (`move`) and add tickets (`add`), all in its own project. Adding an agent or giving one a role, which writes a system prompt, and creating a ticket, which publishes text the session chose under the user's account, wait for the user (see `taskman add` and "Agents create tickets with the project's account"). The inbox checks ticket keys again, as anything that can write the state folder can leave a request.
- **A session keeps to its own project** (`cli::confine`, by `TASKMAN_REPO`). People keep a public project, where strangers write issues and PRs, beside a private one on a work tracker; text read in the first shouldn't have a session read the second's tickets with its account, or open sessions in its repository, without a prompt. So `status`, `add` and `move` refuse another project, whether named with `--project` or picked by the key's prefix; in a session `status` reads a key from the session's project only, not even the same Jira or Linear issue another project has open (which would show that project's worktree and PR). The check is in the code because Claude's rules can't do it: they match the command's text, and an `ask` rule on `--project` was let through by `--proj""ect`, which the shell reads as the same thing (checked with Claude Code 2.1.304). Going wider takes `env -u TASKMAN_REPO` in front of the command: no rule matches that, or any command that changes the environment first (`unset`, `export`, `VAR=`), so Claude asks the user, who sees the whole command. Refusing outright would have taken away a documented use, `taskman status ENG-52` for any ticket, which the user's own shell keeps (in Claude, `! env -u TASKMAN_REPO taskman status ENG-52`: a `!` command has the session's environment).
- **The Local files board follows no links.** A repository could commit `workplan/todo/ENG-1-x.md` as a link to `~/.aws/credentials`; listing takes regular files only, and reading opens with `O_NOFOLLOW`. Columns are real folders only, and so is the board: `workplan` itself committed as a link to a folder elsewhere would make its folders columns and its files tickets.
- **Local folders are the user's.** The state folder (inbox, status files) and the config folder are 0700. The hook command quotes the binary's path for the shell. Still, the inbox takes requests from regular files of up to 1 MiB only, opened without following a link or waiting on a pipe: a pipe left there (by mistake, or by something running as the user, which SECURITY.md leaves out of scope) would otherwise hang the UI thread on its next poll. Saves (`store::write_atomic`) sync the file before renaming it over the old one, so a crash can't leave an empty tickets.json under the name; the heartbeat, rewritten every second and read only for its time, skips the sync (`write_unsynced`). And a token an older version saved as typed is never shown in a picker; the label says to fix it in Settings.
- **Known and accepted:** sessions inherit taskman's environment, so a token taskman reads with `env:VAR` is visible to every session, as it is to anything the user runs from that shell; use `keychain:` or `cmd:` (a private file's `cmd:cat` included) to keep it out of the environment. A session runs as the user, so it could still run the same command, read the same keychain item or the same file. A session can still be misled by what it reads in other ways (files in the repository, web pages); the label helps the model, but only the user's approvals stop it. A selector after each emoji, or a joiner or none between letters outside ASCII, still carries a bit or so per character; that is too slow and too rare a channel to be worth breaking the text that uses them.

## taskman creates each ticket's worktree

taskman used to only find worktrees. A ticket without one ran in the main checkout, so parallel sessions shared files and branches, Codex's sandbox asked approval for every edit in a worktree it made itself, and nothing told a session how to name a branch so it could be found. Now adding a ticket creates its worktree (src/worktree.rs) and the session starts in it.

- **taskman runs git, not `claude --worktree` or `codex --worktree`.** taskman needs the folder and branch before the session starts: the session's folder, resuming, the PR lookup, `taskman status` and the agents' briefs all use them. Claude's flag names the branch `worktree-<name>`, which no tracker links (a `WorktreeCreate` hook could rename it, but then taskman names it anyway), and a named session, which every taskman session is, asks keep or remove on exit, where remove deletes the branch and its unpushed commits; there's no setting to skip that. Codex's flag takes no name and picks its own folder. Doing it in taskman also keeps Claude and Codex the same.
- **The branch is configurable, the folder has a default.** The branch is seen by the team, the tracker and CI (branch protection, `feature/*` rules), and conventions differ, so it is a per-project format. `{tracker}` (the default) uses the tracker's own name: Linear's `branchName`. Jira has no team-wide branch template (its "Create branch" format is per user), so taskman's format fills the gap; Jira's default puts the key in capitals because Atlassian's docs say lowercase keys don't link. Formats must contain the key, or neither the tracker nor `find_worktree` could link the branch. The folder is private to you, so it is a choice of two, not a format.
- **Beside the repository by default,** `<repo>-<KEY>` as Claude Code's docs show for manual worktrees. Inside it (`.claude/worktrees/<KEY>`, where `claude --worktree` puts them, and where Claude's EnterWorktree tool looks) is one choice away. Inside, the worktree would show as untracked in the main checkout and tools run there may scan it, so taskman excludes the folder in `.git/info/exclude`, which is local, never in `.gitignore`. It appends its line and leaves the file alone when it can't be read: an earlier version rewrote it from a read that took a file with one byte that isn't UTF-8 as empty, and so deleted the user's own rules.
- **From the latest default branch.** `git fetch origin`, then `origin/HEAD` (asking the remote when a remote added by hand never set it), like `claude --worktree`. Without a remote, or when the fetch fails or takes over 30 s (the session is waiting), the local `HEAD`, and a toast says so.
- **The session waits, the UI doesn't.** Creating runs on a thread and the Claude pane says so; the tracker fetch that gives the branch name also fills the tracker panel. `Ticket::cwd` stays the main checkout until the worktree exists, but the session doesn't start there: `Ticket::pending_worktree` holds the request, saved, so a quit midway carries on at the next start, and a failure waits for Retry (Enter) or the user choosing the main checkout (`ctrl+a M`). A result is matched by its creation id (`TicketView::creation_id`), not the key: a ticket closed and added again while git ran is another ticket, and the old result goes as its close said. Falling back silently once let a session edit the shared checkout, other sessions' branch included.
- **A half-made worktree is made again, never used.** A `git worktree add` stopped partway, at taskman's 300 s limit (a big repository, Git LFS or WSL's `/mnt/c` can take that long) or by a kill, leaves the folder listed on its branch but locked as `initializing`, with nothing in its index: every file looks staged for deletion, and a session's next commit could delete them all. Adopting the folder because git lists it on the branch once did just that. Now `create` removes such a worktree (`git worktree remove --force --force`; its checkout never finished, so it holds no work) when its own add fails and before using a folder that's already there, keeping the branch for the next try, and `find_worktree` never offers one (`Worktree::unfinished`). git writes the lock reason in the user's language, so taskman runs `worktree add` with `LC_ALL=C`; one that git started elsewhere in another language isn't recognised.
- **taskman's own worktrees are marked before git runs.** Closing offers to remove only a worktree taskman made, and a folder that already is the branch's worktree when `worktree::create` looks is someone else's (`Created::made` false), such as one made by hand. The exception is one taskman made itself and quit before recording: git runs in its own process group, so a quit (or a crash) doesn't stop it, and the worktree it finishes is found there at the next start. So `create_worktree` saves the folder in the ticket's pending worktree (`PendingWorktree::making`) before git runs, and a folder found there that the mark names counts as made; a failure clears the mark, as git leaves nothing behind, so a worktree made by hand in its place before the retry stays the user's. The mark is in tickets.json, beside the request it belongs to, rather than in git: `git config --worktree` needs `extensions.worktreeConfig` set in the repository's shared config, the user's, after which git's docs say values such as `core.bare` and `core.worktree` must move out of it; and a file in the worktree's admin folder (`.git/worktrees/<name>/`) can only be written once git has made it, which is the very window it has to cover. Older builds read the field as an unknown one and keep it, and tickets saved before it keep their `created_worktree`.
- **Per ticket, defaulted per project.** The Add form decides; the project setting is its default, "Create one" unless the project says otherwise. A project whose workflow creates its own worktrees (on branches like `change/<KEY>`, which `find_worktree` already picks up) sets "Don't create" once; it is saved as `Some(false)`, so it never depends on what's in the repository. A key that already has a worktree uses it, and the form shows which.
- **Few settings, an escape hatch later.** taskman owns what it must know before a session starts (the folder and branch) and takes the rest from the tools: the tracker's branch name, origin's default branch, Claude Code's folder layout. A setting exists only where teams differ and taskman can't infer it, which is the branch format. Setting a worktree up (`.env`, dependencies) belongs to the repository's tooling or the user's Claude setup, not to taskman. A team whose needs these don't cover gets a per-project command rather than more settings (roadmap).
- **Nothing is ever lost.** A folder that exists and isn't the ticket's worktree is left alone. Closing a ticket offers to remove its worktree only if taskman created it (`Ticket::created_worktree`; not when git found the branch already checked out there, `Created::made`) and only when nothing would be lost: no uncommitted, untracked or ignored files, and no commits that are on no remote and not reachable from the merged PR's head commit (`headRefOid`). A squash merge leaves the branch's own commits on no remote once GitHub deletes the branch, so the PR's head vouches for them; "the PR merged" alone doesn't, as commits made after the merge are in neither, and a PR found by mistake would vouch for anything. A head commit the clone never fetched proves nothing. The local branch goes only when merged (its HEAD within `origin/HEAD` as last fetched, or within the PR's head). The check reads local git only, so it runs as the dialog opens; the dialog's answer is stale by the time `r` is pressed, so removal stops the session, waits until its CLI is gone (it ran in the folder; see "Stopping a session"), checks again and keeps everything unless the result is the same commit and still safe. `git worktree remove` without `--force` refuses a worktree with changes, and the branch is deleted with `update-ref -d <ref> <checked commit>`, which fails if a commit landed in between (`branch -D` would delete whatever it points at). The check asks `git status` for untracked files and submodule changes outright (`--untracked-files=normal --ignore-submodules=none`): `status.showUntrackedFiles=no`, common in big monorepos, hides new files from `git status` and from the status git runs itself before `worktree remove` deletes, so a new file would go with the folder; the removing git has the setting overridden too (`-c status.showUntrackedFiles=normal`), as the last guard. A worktree with submodules git refuses to remove at all. Edits to files marked assume-unchanged or skip-worktree (`git update-index`, `core.ignoreStat`, a sparse checkout) are hidden from `git status` too, as people keep local edits to config files that way, and `git worktree remove` deletes them with the rest: the check lists them with `git ls-files -v` and hashes the ones on disk against the index; one off the disk, as a sparse checkout leaves most skip-worktree files, holds nothing. Worktree paths are compared after resolving symlinks, since git lists real paths. Removal holds the ticket's owner lock (`App::close_at`), which keeps a new session out of the folder while git deletes it, or doesn't happen: when the lock can't be taken (the state folder can't be written, say) the ticket still closes, but the worktree stays and the toast or the `taskman close` reply says why. The worktree taskman created stays the ticket's: a PR refresh moves a ticket that never started into the worktree git finds for its key, but not once taskman has made one, since the lookup prefers a branch ending in `/<KEY>`, as workflows name theirs (`change/ENG-52`), and closing would then offer a folder and branch taskman didn't make; `created_worktree` never comes to describe another folder, and `taskman status` names that worktree too, not the lookup's. Keeping is Enter and removing is `r`, so the familiar key never deletes. Ignored files are the trap: `git status` leaves them out, and `git worktree remove` deletes them without `--force`, so a clean, merged worktree would take its `.env` or local database with it. The check lists them with `git ls-files --others --ignored --exclude-standard --directory` (a folder of nothing but ignored files as one entry) and lets through only folders tagged as caches by the Cache Directory Tagging spec, checked by the tag's signature rather than its name. There's no list of names like `node_modules` or `.venv`: those can hold work or take long to rebuild, and a list would always be missing someone's. The one exception is the files an OS writes into folders it shows, `.DS_Store`, `Thumbs.db` and `desktop.ini`, matched by exact name in any folder: they never hold work, and global gitignores ignore them, so without it nearly every worktree opened in Finder would stay. A folder git reports whole still counts, even if it holds only those. Nor does an ignored symlink count: a link holds no content, and `git worktree remove` deletes the link, never what it points to, so the notes maintainers link into every worktree (`CLAUDE.local.md`) don't keep it; git lists a link without a trailing slash even when it points to a folder, and the check looks at the link itself (`symlink_metadata`), not its target. When ignored files are all that's left, the dialog offers `d`, a different key that says it deletes them; the list is part of what removal checks again, so a file written after the dialog opened keeps the worktree. `taskman close` has no such option: agents run it, and deleting files nothing else has a copy of should be a person's call, made in the dialog. Claude Code removes an unnamed session's clean `--worktree` on exit without asking; taskman asks, because you may have the folder open in an editor.

- **A session never starts in a folder that's gone.** portable_pty runs a command whose folder isn't there in the home folder instead, without an error, so a worktree removed by hand or a project folder that was moved had the CLI work in `~`, believing it was the ticket's checkout, with a resumed conversation carried along. `start_session` checks the folder (`Gone::of`) and refuses, and so does `taskman resume`, where the spawn would fail as though the CLI weren't installed. The check comes after the owner lock is taken, so a session running in another terminal still shows as that; the lock is let go unchanged. Enter makes a gone worktree again where it was, on its own branch (`PendingWorktree::folder` and `branch`), whatever the project's settings say now, since that's the branch its PR and its conversation know. git still lists a worktree removed by hand, and adds none in its place until it's let go: `worktree::create` runs `git worktree remove` on that one folder, which holds nothing to lose, rather than `git worktree prune`, which would also drop worktrees on a drive that isn't mounted. A locked one is the user's to unlock. A project folder that's gone is the user's to put back, since its path can't be changed in Settings. gh run in a folder that's gone fails with the same error as a gh that isn't installed; that error now says the folder is gone, rather than turning the project's PR panels off as "gh isn't installed".

## Stacked tickets: taskman records the base, git and GitHub do the rest

A ticket that builds on another's unmerged work needs its worktree started from that ticket's branch, its PR opened against it, and someone to notice when the base merges. taskman does those three and stops there (src/stack.rs).

- **The base is saved with its branch** (`Ticket::base`), because the base ticket is often closed once it merges and the brief and hints still name the branch. It's saved only when the worktree really started from it: a branch that already existed is checked out as it is.
- **The newer of the local branch and origin's.** The base's session may not have pushed its last commits, so origin alone could start the stack behind; someone may also have pushed more. When they've diverged, origin's, which is what the PR targets. A base branch that's gone everywhere has most likely merged, so the worktree starts from the default branch and isn't stacked.
- **The PR's own target is the signal.** The sidebar shows `baseRefName` when it isn't the default branch, rather than what taskman saved, so it shows what GitHub will actually do: GitHub retargets the upper PR to the base's base when the base's branch is deleted after merging (documented, and seen with a squash merge), and the arrow then disappears by itself. Whether the base merged comes from the base ticket's PR while it's open, else from the PR having moved off the base's branch, so no extra `gh` calls run. The one state worth a warning is the base merged with the PR still on its branch (the repository doesn't delete merged branches): merging then lands in a dead branch.
- **No rebasing, no restacking.** After a merge commit nothing is needed; after a squash merge the upper branch still holds the base's original commits and needs a rebase onto main, which can conflict, so it's the session's or the user's call. GitHub's own stacked PRs (in preview since July 2026) rebase the upper branch on GitHub's side, which leaves the local worktree behind. So the brief says from the start: if a push is refused after the base merges, pull with rebase rather than force-pushing. Restacking whole chains is left to git, `gh stack`, Graphite or git-spice, which a session can run in its worktree.
- **Nothing is sent to a running session** when the base merges: that would spend tokens the user didn't see. The panel and `taskman status` say it, and a session started later gets it in its brief.
- **An older running TUI can't drop `--on`.** After a background update, `taskman add` runs the new binary while the TUI is still the old one, which would ignore a field it doesn't know and add the ticket on main. The TUI writes its version and inbox format into `inbox/alive`, the command refuses `--on` when the TUI is older and says to restart it, and the TUI refuses requests with unknown fields, so a later option fails loudly instead of half working.

## Finding a ticket's PR

The lookup collects PRs on the ticket's branch and PRs whose title or branch mentions the key as a whole (not after a letter or digit, not before a digit: `ENG-5` isn't in `ENG-52`), then shows the newest open one, else the newest merged one, the branch's own before those that only mention the key. A wrong match isn't just a wrong panel: the merged PR decides what closing may delete. A PR closed without merging counts as no PR (the panel notes it), so abandoned work doesn't look live. A ticket without a branch takes its open PR's head branch, unless the PR comes from another repository (`isCrossRepository`, taken as true when GitHub doesn't say): its author named that branch, and on a public repository anyone can open a PR that says it closes the issue. The PR still shows. A remembered branch that exists neither locally nor on origin, with no open PR, is forgotten. Branches come from git worktrees first: a branch ending in `/<KEY>` (how workflows that create their own worktrees tend to name them, like `change/ENG-52`), then any branch containing the key as a whole.

**One query per repository.** Each refresh lists the PRs of every due ticket in a repository in one `gh api graphql` call, with an alias per ticket: the PRs on its branch (`pullRequests(headRefName:)`, as `gh pr list --head` asks) and the search for its key (`search`, as `gh pr list --search` does). A gh process costs about 130 ms of CPU and 40 MB, more than taskman itself; ten tickets used to run ten to twenty of them a minute just to find their PRs (`--search` ran when the branch had no open PR). The search runs even when the branch has an open PR, which is then ignored, so the results are the ones the two calls gave. A repository-wide `gh pr list --state all` would be one call too, but returns thousands of PRs in a busy repository. The repository is still gh's: `{owner}` and `{repo}` in `-F` values are filled in by gh from the folder, as `gh pr view` resolves it, and only the host comes from `github::default_repo`, as `gh api` doesn't take it from the remotes. Branches go as `-f`, plain text, since `-F` reads a file for a value starting with `@`. At most 20 tickets go in a query, as GitHub runs each search on its own and fails a query that takes over 10 s. One failed query fails the refresh of all the tickets it asked about, and their panels keep what they showed; so does a panic in the repository's lookup thread (`Reporter::send_lookups`), with one toast naming them. `git worktree list` runs once per refresh too.

**Details only when the PR changed.** The PR found is shown in full: checks, reviews, comments and review threads, from one `gh api graphql` query per PR (`github::view`) in the repository its URL names, which replaced `gh pr view` and a second query for the threads. The list query also reads each PR's `updatedAt`, head commit, the head commit's check state, mergeability, draft flag and review decision (`github::Stamp`), and a ticket's lookup carries the PR it shows (`Wanted::shown`): when the PR found is that one with the same stamp, its details are kept rather than fetched (`github::unchanged`). GitHub moves `updatedAt` for a comment, a review, or a change of state or title, the head commit shows a push, and neither moves for a check finishing: the check state covers checks, though only when the overall state changes, so a check passing while others still run doesn't count. Mergeability is there for what happens to every open PR after a merge: GitHub doesn't move `updatedAt` when a PR starts conflicting with its moved base, and users act on that. The draft flag and review decision are there because the sidebar shows them, and one may change without moving `updatedAt`. `mergeStateStatus` isn't: nothing shows it, and it moves with things that don't change the screen (behind its base, or blocked on required reviews and checks), so it would only add fetches. Unasked, GitHub answers `UNKNOWN` for mergeability and keeps that until something computes it, so it doesn't flap between refreshes. So the selected ticket fetches its details on every refresh, as does a refresh someone waits on: `ctrl+a r`, and the hook's signal after Claude pushed or ran gh (`sync::keeps_details`); a background ticket catches up on the rest when it's selected. Details whose threads GitHub didn't send, a PR GitHub sent without a stamp, and `taskman close`'s lookups (the PR decides `--merged`) are always fetched. With ten unchanged PRs in the background that's one gh process a minute, the list, where it was 21 (and 30 before the list was batched). Each unchanged PR's details are a clone of what the panel shows, sent to the lookup thread and back, so the reply is self-contained and `take_pr` handles it as any other.

The repository is `gh`'s choice, not a setting: `gh` resolves it from the folder's git remotes, so taskman and every session agree. Settings names it (`github::default_repo`, git only) by following `gh`'s rule: the remote `gh repo set-default` marked (`remote.<name>.gh-resolved`), else the first of upstream, github, origin, then the rest, which is what `gh` does without a terminal. An editable repo field would drift from the remotes and couldn't make `gh` work in a folder without a GitHub remote; changing it goes through `gh repo set-default`.

## Slow calls stay off the UI thread

Every frame and every session's output goes through one thread, so network calls and token commands run elsewhere; only quick local git reads (worktree lists, say) stay on it. Saving an account tests it, and saving a Jira project checks its key, on a thread: the form says it's checking and submits itself again with the answer (`Form::checking`), unless it was edited or left meanwhile.

taskman's git, gh and token commands go through `proc::run`: stdin from /dev/null, a session of its own (`proc::own_session`), git, gh and ssh prompts off, and a time limit after which the whole group is stopped (with the `kill` system call on the group, not the `kill` program, which slim container images lack): 30 s for gh and network git, 5 min for other git (a big checkout and its hooks), 60 s for a `cmd:` or `keychain:` token (time to unlock a password manager or keychain in its own window). The limit matters beyond the wait: a ticket doesn't start a refresh while one is in flight (`Remote::due`), so one call that never returned used to stop that ticket's refreshes until restart. The updater uses it too, `proc::run_with_input` piping the download into `tar`: one limit covers writing the input, reading the output and stopping the group, so a program that doesn't read its input, or leaves something behind holding its output, ends at the limit.

The session of its own is what keeps a helper off taskman's terminal. A process group alone, which `proc::run` used before, isn't enough: the helper stays in taskman's session, so it can open /dev/tty, and with raw mode leaving TOSTOP off it can write there too. ssh asking for a key's passphrase (as `git fetch` does with a key that isn't in ssh-agent) printed its prompt over the screen dozens of times, read the keys meant for taskman, and spun at a full core until the time limit. In a session of its own, with no controlling terminal, opening /dev/tty fails, so ssh, gpg's pinentry-tty or a token command that asks on the terminal fails at once. ssh then tries an askpass program on the desktop, kept for users who set `SSH_ASKPASS` (some desktops do) and otherwise turned off (`SSH_ASKPASS_REQUIRE=never`), as ssh's built-in default is a bare X window nobody asked for. The worktree fetch reads git's error and says what to do (`worktree::fetch_error`): load the key into ssh-agent, accept a new host in a terminal once, or set up a credential helper. The clipboard commands start in a session of their own too. A helper in a new session still leads a process group whose id is its pid, so stopping the group at the limit works as before. The cost is the spawn: std can't start a session through posix_spawn yet (`Command::setsid` is unstable), and the `pre_exec` that calls `setsid` makes it fork instead, which copies taskman's page tables: about 15 ms a helper rather than 1 with 300 MB resident (measured on WSL2). taskman runs a few helpers a minute, nearly all on background threads, so it was worth it; switch to `Command::setsid` once it's stable.

taskman's own HTTP requests (Jira, Linear, the updater's downloads) take their agent from `net::config`, so they share what one of them learned: a limit on each request as a whole (20 s for a tracker), a guard that keeps unit tests on the local test server, even through an App's background fetch, and one more try when a connection drops under a request that can safely run twice (`net::retry_dropped`): a tracker's reads and every updater request, never a create.

## Notifications when you're away

A session waiting on a permission prompt can sit for minutes while you're in a browser or an editor, and the terminal's bell is often muted or unseen. So when a session starts needing you and you're away, taskman sends a desktop notification (`notify.rs`, from `App::started_waiting`).

- **Away is what the terminal says.** taskman turns on focus reports (`CSI ?1004`, crossterm's `EnableFocusChange`) and keeps the last one (`App::focused`). Unfocused, every session that starts waiting notifies, the one on screen too, since you can't see it. A terminal that never reports (tmux without `focus-events`, older terminals) leaves it unknown, and then only a session out of sight notifies, as the bell does: guessing "away" would notify while you watch, guessing "here" would never notify. Idle time was considered as a fallback and not used: reading a long answer looks the same as being gone.
- **Once per wait.** It's sent as the state turns "needs you" (`TicketView::hook_reported`, or an answered prompt that is still waiting), not on every poll; Claude's 6 s reminder of the same prompt isn't a change of state.
- **The terminal's own first where it shows them.** OSC 9 in iTerm2, WezTerm, Ghostty and kitty: clicking it goes back to that window, which a desktop command can't do. Over SSH only OSC 9, as a command would notify the server's desktop. Otherwise the desktop's command, and OSC 9 when none works, as the clipboard falls back to OSC 52. Inside tmux the outer terminal isn't known and tmux drops OSC 9 unless `allow-passthrough` is on, so the desktop's command comes first there; OSC 9 goes through tmux's passthrough. OSC 777 was the other choice: fewer of these terminals show it, and sending both would show two in the ones that show both.
- **WSL gets a Windows toast.** WSLg has no notification service (`notify-send` fails at once), so taskman runs `powershell.exe` with the toast's script as `-EncodedCommand`, under PowerShell's own app id, which needs no registration. The text is in the script as base64, so no quoting can break out of it; on macOS and Linux it's an argument, with no shell.
- **taskman's words only.** The notification says the key (or agent's name) and why: `ENG-52 needs you: a permission prompt`. The command a prompt asks to run is the CLI's text, which may come from a tracker or a file, so it stays out (see "Untrusted text"); the key goes through `untrusted::line`.
- **On by default.** It fires only when you've left and something waits on you, at most once per wait, which is when it's wanted; a setting off by default would go unfound. Settings → General turns it off, or to the terminal's own only.
- The commands run on a thread through `proc::run` with a 10 s limit (powershell.exe can take seconds to start); the escape is written by the UI thread on its next pass, like OSC 52.

## Refreshing and what counts as "new"

The selected ticket refreshes its tracker every 30 s and GitHub every 20 s; the others every 3 min and 1 min. Switching to a ticket, Claude finishing a turn, or a refresh signal from the hook refreshes sooner. A repository's PR lookups share one query (see "Finding a ticket's PR"), so when one of its tickets is due, the others three quarters of the way there (45 s in the background, 15 s when selected) join it: tickets that fell out of step, by being selected or refreshed on a signal, fall back in instead of each running a query of its own. Routine refreshes are silent; a spinner shows only when the user is waiting (ctrl+a r, switching to stale data, a refresh Claude triggered, the first load). Freshness is shown in minutes so the label doesn't tick every second.

A panel takes only the reply of the latest fetch it started. Each fetch gets an id from one counter (`App::fetches`), kept on the panel's `Remote` and carried in its reply (`Msg::Jira`, `Msg::Pr`); a reply with any other id is dropped. Matching replies by ticket alone let a late one overwrite newer data and mark it fresh: a project moved to another workspace while a fetch was out showed the old workspace's issue as current (changing the tracker empties the panel, so nothing from before is wanted), and a PR lookup that spanned a close and re-add landed on the new ticket, which is a new `Remote`. It's the scheme worktree creation uses (`TicketView::creation_id`). A `taskman close` lookup starts over a routine fetch in flight, so the routine reply is the stale one. The one fetch that may never report, worktree creation's while a token is still being read, is expected without a spinner and never over a fetch in flight, so a dropped reply never leaves `loading` set with nothing to clear it. The Add form's lists of a project's open issues take ids from the same counter (`add_form::Listing`), and a list is kept only while its folder waits on that id and the project's tracker is still the repository asked: a list that landed after the tracker moved to another repository, or after the project was deleted, would have let a title pick the old repository's issue number.

Comments and reviews are "new" until the ticket is selected: selecting it marks everything loaded as seen (`TicketView::mark_seen`), whatever its panels show, and so does a fetch that lands while it's selected (`App::mark_selected`, also for a selection that moves without `select`: a close, a removed project). What was new keeps its `●` (`TicketView::fresh_jira`, `fresh_gh`, in memory only) until the ticket is left or `ctrl+a m`, so the panels still show what arrived. The first fetch for a ticket counts everything already there as seen. Marking used to wait for the user to leave, and to go by the panels shown; a count of what a hidden panel held then never cleared, which read as a bug. The seen ids are added to, never replaced: replacing them with what was loaded at the time made read ones new again after a moment with fewer loaded, such as the PR lookup settling on another PR that mentions the key, and a count that never cleared was reported.

## Handing a session to another terminal

The embedded terminal can't do everything a real one can: a full-screen CLI keeps its history itself (see "Selecting and copying text"), and the user's terminal has its own search, size and features. `ctrl+a t` hands the session off and `taskman resume KEY` (src/resume.rs) continues it wherever the user runs it.

- **Not `claude --resume <id>`.** A bare resume loses what taskman adds at every start: the brief (not in the transcript), the hooks that drive the sidebar, `--name` that agents message, the environment (`TASKMAN_STATUS_FILE`, `TASKMAN_TICKET`, the `taskman` link on PATH) and the folder (Claude keeps transcripts per folder). So `App::launch` builds all of it once, for the pane and for the command: the command builds the TUI's state from the saved files alone (`App::resume_launch`, no tokens, PR fetches or updates) and runs the same launch in the user's terminal. The pane adds only what its emulator needs (`TERM`, and no `TMUX`). A brief built this way lacks the PR states only the running TUI has in memory.
- **A hand-off, not a second copy or a fork.** Two CLIs on one conversation would interleave their turns into one transcript, and a fork (`--fork-session`) would leave the ticket with two conversations. So one copy runs at a time, and the other side refuses. Whoever runs it holds an `flock` on `<KEY>.owner` beside the status file and writes who it is (`taskman`, `outside <pid>`); the system drops the lock however the process ends, so a crash or a closed terminal leaves nothing stale. What the file says once nobody holds it tells "back" (it last ran outside, or was handed off) from a ticket the TUI may start as usual. The TUI checks tickets it doesn't run on every status poll; a lock seen held is tried again for a few milliseconds, since a process forking at that moment (taskman runs git, gh and clipboard commands) shares the file until it execs.
- **The lock fails closed.** A lock that can't be taken (a state folder that can't be written, say) stops the session starting, in the pane and from `taskman resume`: started without it, a second copy could run on the same conversation, which is what the lock is for. The pane says why, and Enter tries again.
- **Outside, the CLI holds the lock too.** `taskman resume` waits for the CLI, and a lock only it held went with it when it was killed, while the CLI ran on: a second copy could start. The CLI inherits the locked descriptor (close-on-exec cleared in the child only, so a git that another thread starts at that moment doesn't get it), the file names the CLI's pid, and letting go is an explicit `LOCK_UN`, which frees every copy: processes the CLI started inherit it too and would otherwise keep the session claimed after it ends. Only if `taskman resume` is killed and the CLI then ends can such a process keep it claimed, until it ends. The pane's CLI doesn't inherit it (portable-pty closes the child's other descriptors), and doesn't need to: taskman ending closes its terminal, which hangs up the CLI. A restart (`prefix R`) keeps the pane's claim rather than taking it again, which would find it held by taskman itself.
- **Quitting, not killing.** `ctrl+a t` sends the CLI a hangup, as closing a terminal would, and waits up to 5 s for it to exit before stopping it; stopping a session gives it only a moment (200 ms, then SIGKILL), on a thread of its own, which also reaps it: waiting on the UI thread would freeze the screen, and an ended CLI nobody waited for stays a zombie until taskman quits. At quit every session is stopped together and waited for (`session::stop_all`), so it takes a moment in all. Claude Code runs its SessionEnd hook on the hangup; Codex 0.162 exits without its hook.
- **Stopping a session: nothing takes the CLI's place until it's gone.** Moving the kill off the UI thread opened a window of up to 200 ms in which the stopped CLI still ran, and the owner lock is taskman's, not the CLI's, so it kept nothing out: a restart (`ctrl+a R`) started the next copy on the same conversation, closing a clean ticket removed the worktree the CLI was running in, and a hand-off let `taskman resume` start a second copy. So the thread that stops a CLI is kept, as the ticket's `Reaper` (`TicketView::stop_session`), until the CLI is reaped. `start_session` doesn't start a ticket that's still reaping, and the next tick tries again; a ticket closed and added again within the window takes its reaper back (`App::keep_reaper`). A worktree removal joins the reaper before `git worktree remove`, on its own thread as before, from the dialog and from `taskman close` alike. After a hand-off the claim stays held until a poll finds the CLI gone; the owner file reads `handed-off` while locked, which is `Owner::Stopping`: not elsewhere, so the ticket can still close, and `taskman resume` waits up to 3 s for it rather than refusing, since the tmux window a hand-off offers runs it at once. Quitting waits for every reaper still running (`App::stop_sessions`), not only the live sessions'. The tests in `tests/stopping.rs` run a stub CLI that goes on after the hangup, as a CLI busy finishing does.
- **A rename claims the new name first.** `ctrl+a e` restarts an agent's session under its new name (Claude takes `--name` only at startup), and `taskman resume` finds sessions in the saved state, so the new key is what it asks for once the rename is saved. Saved with nothing holding the new key's owner lock, the command could start a second copy of the conversation while the old CLI was still stopping, and did (seen with v0.4.29, from the TUI and from `taskman resume`). So `rename_agent` takes the new key's lock before anything changes and keeps it on the ticket as the pane's claim, which the restart uses as `ctrl+a R` does; a new name whose lock is held elsewhere or can't be taken refuses the rename, with nothing changed. The rename is then saved before the session stops; a rename that can't be saved is undone, the old name kept and still claimed and the session running, and the form says why. The old key's claim (the pane's, or taken for the rename, since another terminal may have started the session since the last poll) goes once the rename is saved, not once the old CLI is reaped: nothing can ask for the old name any more, and the stopping CLI's conversation is the renamed agent's, kept to one copy by its reaper and the new key's claim. A `taskman resume` that read the state just before the save reads it again once it holds the claim, and gives up when the session it found is gone.
- **The same conversation id.** Claude keeps the id on `--resume` (without `--fork-session`), and Codex keeps it on `codex resume <id>`, appending to the same rollout file (both checked with Claude Code 2.1.296 and Codex 0.162). The hooks record the id either way, so taskman resumes whichever the outside run ended on; the command prefers the status file's id to the saved one, as the hooks write it first.
- **Nothing comes back by itself.** A session that came back waits for Enter: the user may still be reading it in the other terminal, and starting it costs a CLI start. `taskman resume` keeps its terminal's signals from ending it before the CLI does (ctrl+c and the hangup go to the CLI), so it lets go of the session only once the CLI has ended.
- **tmux only.** Inside tmux, a new window is one command, so taskman offers it; it passes taskman's own variables (`XDG_STATE_HOME`, `TASKMAN_CONFIG`, ...) with `-e`, since a window gets the tmux server's environment. Opening other terminal emulators would need code for each, so the command is copied instead.
- **Later:** `taskman resume KEY` from a fresh terminal asking the running TUI to hand the session over, which needs an inbox format bump.

## Sleeping sessions

Every session is a full CLI process, a few hundred MB with its MCP servers, and taskman used to stop none until quit: many open tickets exhausted the memory of a WSL machine, which gets only part of the RAM by default. Stopping loses nothing, since a session resumes its conversation when started again (as after a restart, when nothing runs until selected), so a session nobody has looked at for a while is put to sleep, as browsers do with background tabs.

- **Who sleeps** (`sleep::due`, a pure function over `Facts`): a session whose state is idle or your turn, not the selected one, not selected for the set time (counted from when it started or was last selected), and settled (below). Never one that's working, needs you, handed off or outside, or whose last CLI is still being reaped. Agents never sleep: there are few (one per project), they wait for messages from the ticket sessions, and a sleeping agent can't be messaged, so the sessions it coordinates would have nobody to report to. They still count towards the cap.
- **Stopping** is a restart's: `TicketView::sleep` calls `stop_session`, so the reaper keeps a new session off the conversation until the CLI is gone, and the owner lock is kept until then. Once it's gone the lock is let go as after a hand-off, so `taskman resume` can continue the session in another terminal. The ticket's state stays as it was, with `asleep` set (not saved: after a restart nothing runs until selected). A finished turn nobody had looked at still shows as "your turn" in the sidebar.
- **Waking** is `start_session`, as after a restart: the selected ticket starts when dormant (not started, or asleep). A project agent's auto-start (see "Sessions are named") skips sleeping sessions, or sleep would be undone within a tick; the agent's brief says so.
- **Telling agents:** the hooks' file can't say it, since the stopped CLI's SessionEnd hook writes "ended" into it. `TicketView::sleep` writes `<KEY>.asleep` beside the status file first, and `taskman status` reads it as "asleep". Starting a session, a hand-off, closing and taskman's next start remove it with the status files.
- **Background work keeps a session awake.** Claude's hooks report nothing for a `run_in_background` command, a dev server or a watcher, so the CLI's process tree is looked at (`proctree::descendants`: `ps -A -o pid=,ppid=,stat=`, the same on macOS and Linux, through `proc::run` on a thread, answering with `Msg::Scanned`). Once a session has settled after starting (30 s, or a quarter of the setting when that is shorter), its descendants are its baseline: the CLI's own MCP servers and helpers. When a session is due, any descendant not in the baseline is work in progress and it stays awake, looked at again a minute later (half the setting when that is shorter). Zombies don't count. A look that fails changes nothing, and the answer is checked against the session's start and the decision is made again when it arrives, so a session selected or started meanwhile is left alone.
- **Limits:** work started during the settling time is taken as the CLI's own, so a session that is busy from its first prompt may sleep with a server running (resuming restarts the CLI, not what it launched); a process that detaches (double-forks, `setsid`, `nohup` under a service manager) is no longer a descendant and isn't seen; a pid reused by new work is taken as the old one; and work a CLI does inside its own process (a long-running MCP call) is only visible through its state, which is working then.
- **Ended sessions** aren't put to sleep: there is no CLI to stop, and the pane must go on saying it ended. But an exited session keeps its whole emulator, scrollback included (up to 10,000 rows, tens of MB), so once its ending was seen and it was then left unselected for the setting, `due` lists it to be let go (`Due::release`): `TicketView::release_ended` keeps a copy of its last screen without history and why it ended, and drops the session.
- **The setting** is Settings → General → "Sleep idle sessions after", default 1 hour: long enough that a ticket put down for a meeting or a review is still running when you're back, short enough that a day's tickets don't all stay in memory the next day; waking costs a few seconds of startup and nothing else. "Keep awake at most" (default no limit) puts the longest-unselected idle sessions to sleep past that many running, whatever the time; it is the same decision with a second reason, `due`. Both are in config.json and default when missing, so an older file reads as before.
- **Scrollback is taskman's own memory, and is stored trimmed.** Each session's vt100 keeps a history of rows: Settings → General → "Scrollback", `scrollback` in config.json, 10,000 rows when missing (what Alacritty and zellij keep; tmux and kitty keep 2,000, WezTerm 3,500). vt100 kept each row at the width it was written, 32 bytes a cell, though most cells are padding: `git log -p` fills about half of a 77-column row and a third of a 147-column one, and a blank row is all padding. So a busy session's history took 24 MB at 77 columns and 47 MB at 147, and agents never sleep. vt100 0.18 trims a row moving into the history to its last cell that isn't blank with default attributes (a background colour or a link counts), and grows the rows in view back to the screen's width, so drawing, selection, copying and links see the same cells as before. It trims in place, which saves nothing that counts: the freed tail of each row is a hole the next full row can't use, so the memory stays in use. Our fork copies the cells kept into an allocation of their own, and the outgoing row's cells become the new blank row. Measured in vt100 alone (a 40-row screen, 10,000 rows of history, release build, resident memory after a stream of `git log -p` text): untrimmed 25 MB at 77 columns and 48 MB at 147, upstream's trim 24 and 46, the fork's 15 and 19. Measured with one busy stub session before vt100 0.18 (the fork's earlier form of the same copy; whole process, `git log -p` at about 100 lines a second, RSS levelled off): 31.5 MB → 21.6 MB at 77 columns, against 7.2 MB idle, and 54.7 → 26.6 MB at 147. The limit is read when a session starts: vt100 can't change it on a running parser, and a held selection counts the rows dropping off a full history (see "Rows dropping off a full history" under "Selecting and copying text"), which a history shrinking under it would throw off.
- **A full history is taken as one that has dropped rows.** At the oldest row a session still holds, the pane names the key for the CLI's own transcript (`Cli::transcript_key`), where the whole conversation is, so the scrollback limit can stay moderate. vt100 counts the rows it drops but doesn't say (`unbounded_len` is private), and its `on_scroll` callback also fires for rows an `ESC[3J` clears, which aren't worth pointing to. A history at its capacity has dropped its oldest row, or will with the next, which is one row's difference; a clear empties it, so the hint goes with the rows. What this misses: a pane made taller pulls rows out of a full history onto the screen, and the hint waits for that many new rows. Nothing shows on the alternate screen, which keeps no history, and the hint is drawn by taskman, never sent to the CLI.

## One conversation per session

A ticket or agent owns at most one conversation id, and no two share one (src/session_ids.rs). `session_ids::claim` checks it wherever an id comes in: the hooks' reports (`poll_status`), the status files a previous run left (`take_leftover_status`), and before `--resume` (`build_command`, `App::resume_launch`). An id another ticket holds is refused: the ticket keeps its own, and a session that would resume it starts fresh. The hooks stay the source of the id, rather than an id taskman picks with `--session-id`, because `/clear` legitimately gives a running session a new one.

**Why it's checked: a Claude Code race.** With Claude Code 2.1.296, a running interactive session can switch onto the conversation of a second `claude` started later in the same folder. Both then show one conversation, a prompt typed into the first is written to the second's transcript, and the first's hooks report the second's id. The first's own entry in `~/.claude/sessions/<pid>.json` still names its old id. Found while measuring hooks for the inferred states.

- **Who is exposed.** Only sessions sharing a folder: a project's agents, which all run in its main checkout, and the user's own `claude` there. Ticket sessions have their own worktrees, and Claude keeps conversations per folder.
- **Without the check,** the switched agent would save the other's id; after a restart both would resume one conversation and interleave turns in one transcript (what the owner lock prevents for a single ticket), until `tickets.json` was fixed by hand. With it, the switched agent keeps its id, so restarting it (`ctrl+a R`) gives it back its own conversation, and the toast says so.
- **What can't be caught:** a switch onto a session taskman didn't start, such as the user's own `claude` in the main checkout. Its id belongs to no ticket, so the agent takes it.
- **Evidence.** Seen twice, both times with plain `claude` (no taskman flags, Claude's session variables unset) in a fresh `git init` folder. The first session ran `/clear`, an Agent subagent and `/compact`; the second started about 30 s later. The first session's next prompt is in the second's transcript, and its own ends at the compact. The two transcript folders are kept for an upstream report. About 17 other runs, with each step alone, in pairs, or the full sequence with 0 to 90 s delays, didn't reproduce it. ## Input: one prefix key

Every key goes to Claude except after the prefix, `ctrl+a` unless changed, as in tmux and screen. Pressing it shows a menu of the command keys; pressing it twice jumps to the next ticket waiting on you, and `a` after it sends the prefix itself, as screen does. With the kitty keyboard protocol (many macOS terminals), Shift+letter can arrive as the lowercase letter plus SHIFT, so `keys::normalize` folds it before anything matches.

**The prefix is one of a short list** (`keys::Prefix`), not any key: each must reach taskman as itself from every terminal, legacy or kitty protocol (ctrl+\ and ctrl+] arrive as ctrl+4 and ctrl+5 without it), and must not be a key the user can't give up. `a` sends the prefix, whatever it is, because the prefix's own letter may be a command (ctrl+b's `b` folds the sidebar). It is a global (`keys::prefix`) rather than a field, since hints far from the TUI name it too: `taskman status`, `taskman add`, `taskman resume` and errors read it from the config at start. Every hint goes through it; don't write `ctrl+a` in a string. An unknown value in the config falls back to ctrl+a rather than failing the config, which would stop taskman starting. Inside tmux whose `prefix` is the same (`tmux show -gv prefix`, asked off the UI thread; taskman's own environment keeps `TMUX`, only sessions lose it) or inside GNU screen (`STY`; its escape key can't be asked, so ctrl+a is assumed), a toast says so once, remembered in the UI prefs.

**ctrl+z is swallowed, not sent.** Claude Code suspends itself on ctrl+z: it tears down its UI, prints "Run `fg`", stops itself and waits for SIGCONT. In a real terminal the shell's `fg` sends that. Here the CLI leads its own pty session with no job-control shell above it, so its process group is orphaned: the kernel discards the stop, nothing ever sends SIGCONT, and the pane looks frozen while the sidebar shows idle. Sending SIGCONT after forwarding the key was considered, but it races the CLI's own handling (too early and it is lost), and suspending a pane has no use.

## Selecting and copying text

Dragging selects text in the Claude pane or a panel (src/selection.rs).

- **The selection stays after the button is released,** until the next click, key or Esc, as in zellij, WezTerm and kitty. It is copied on release; it used to vanish then, which looked like nothing had been copied.
- **ctrl+c with a selection copies and clears it, and never reaches the session;** the next ctrl+c interrupts as usual (Windows Terminal's rule). Esc clears it, also unsent. Any other key clears it and goes on. Forwarding ctrl+c, as before, sent Claude an interrupt, and two quit it. There is no separate copy key: selecting already copies, and ctrl+c covers the habit. The rules are `selection::key_action`, with tests.
- **Selections are held in content rows, not screen cells** (`selection::Point`): a session's row counts from its oldest history row, a panel's from its first wrapped row. Scrolling, with the wheel or by holding the button past the pane's edge (`edge_step`, on `tick`), keeps the highlight on the same text, and the text can run past what the pane shows, as in tmux, zellij, WezTerm and kitty. While the button is held, scrolling moves the selection's end to what comes under the pointer.
- **The Claude pane holds still while selecting.** It draws a `selection::Snapshot`: the session's history above a copy of its screen from when the selection began, so streaming output can't slide the highlight or change what's copied; a badge says "Esc to resume". History rows never change once they've scrolled off the screen (vt100 0.16 has no `ESC[3J`), so they're read from the live session as needed, a screenful at a time by setting its scroll position, rather than copied: a clone would copy the whole history (10,000 rows by default) on every click. The screen does change, so it is rebuilt from its rows (`contents_formatted`). Text comes from `contents_between`, so rows the terminal wrapped are joined and wide characters come out once.
- **Rows dropping off a full history are counted through vt100's scroll position.** Once the history is full (the scrollback setting's rows), each new one drops the oldest, so content row numbers would shift. vt100 doesn't report it, but while scrolled back it moves the scroll position along with each row added, so the view stays put. The snapshot keeps the live session scrolled back a row and, on every tick, takes rows added minus how much the history grew as rows dropped (`Snapshot::track`). The history's length is `Screen::scrollback_len`: the rows held, since vt100 0.18 (0.17's was the capacity, which is why this once scrolled to the top to find it). When the selection is cleared, the session is left scrolled to where the view was (`Drop`). `Session::screen_count` reads the bottom of the screen whatever the scroll position, since the Interrupted check uses it.
- **The screen is resized before the pty.** `Session::resize` sets vt100's size first and the pty's after: the CLI redraws for its new size as soon as the pty has it, and vt100 0.18 moves rows between the screen and its history on a resize, so a redraw that landed first was taken as drawn on the old screen and overwrote history rows (with a real Claude session, 7 of 40 printed lines went missing from the history after a few resizes; with the order swapped, none did).
- **A session clearing its history ends the selection.** History rows never change, except that a session can clear them: `ESC[3J` (vt100 0.17 and later) empties the history and puts the scroll position at the bottom, and so does a resize, which moves rows between the screen and the history (a resize also ends the selection before this, as the layout changes: `lay_out`). Rows added only ever move the position up. So a position that fell, or a history that shrank, means the rows the snapshot counted are gone or moved, whatever was printed after (the history may even have regrown past its old length), and `dropped_since` says so. `track` then fails with `Lost::History`, the selection ends with a toast, and the session is left at its bottom. The other way out, copying the history rows into the snapshot when the selection starts, would copy up to the scrollback setting's rows on every click.
- **The alternate screen has no history in vt100**, so a full-screen CLI (Codex by default, Claude's full-screen mode) can only have its screen selected, and the wheel does nothing over it while selecting. Codex's `--no-alt-screen` doesn't change that: it prints history through a scroll region, whose lines vt100 drops (see the roadmap). `ctrl+a v` opens the session's history and screen (`selection::session_text`) in `$EDITOR`, through the same hand-off as a Local files ticket, from a file only its owner can read in the state folder.
- **Panels copy wrapped lines whole, scrolled out of view or not.** While a panel holds the selection, its lines are rendered whole at its width (`selection::Panel`), for the rows out of view. ratatui doesn't record where it wrapped, so each line is also rendered alone and its rows matched against the line's text (`selection::wrap_breaks`), which gives what each wrap dropped: a space between words, nothing inside a long URL. Panels scroll as far as their last wrapped row, so the end of a long description can be reached.
- **Clipboard: a command first, OSC 52 last, and the toast says which.** Inside tmux, `tmux load-buffer -w -`: tmux's default `set-clipboard external` drops OSC 52 from programs inside it, while `-w` has tmux pass the text to the outer terminal itself (over ssh too). Otherwise `pbcopy`, `clip.exe` (WSL), `wl-copy`, `xclip` or `xsel`; clip.exe garbles UTF-8 and keeps a BOM, so it gets UTF-16LE without one. Only when none runs is the text sent as OSC 52, and the toast says "Sent to the terminal's clipboard (OSC 52)" rather than "Copied", since nothing confirms the terminal took it. With tmux's `set-clipboard off` the toast says the text stayed in a tmux buffer. The commands run on a thread: clip.exe is slow and any of them could hang. They don't go through `proc::run`, because xclip and wl-copy leave a process holding the clipboard, and it would hold the output pipes open until the time limit.

## Links in sessions

Links a session prints open from the user's terminal; `prefix l` lists them to open or copy (src/links.rs).

- **What the CLIs print** (Claude Code 2.1.296 and Codex 0.162, recorded in a pty): both print links as OSC 8, `ESC ] 8 ; params ; url BEL`, the text, then `ESC ] 8 ; ; BEL`. Claude adds an `id=` param, moves the cursor over the space after the text before closing, and for a link longer than the row closes it at the row's end and opens it again, with the same id, on the next. Codex adds no id, keeps one link open across rows, moving the cursor to each row's indent, and while streaming draws a URL again as it grows. Claude decides on OSC 8 from the environment: `FORCE_HYPERLINK`, `TERM_PROGRAM` (iTerm, WezTerm, vscode, ghostty, kitty, tmux 3.4+ and others), `WT_SESSION`, `VTE_VERSION` or a `hyperlinks` setting; with them it shows only a Markdown link's text, without them `text (url)` as plain text. Codex printed OSC 8 even with none of them set, then as `text (url)` with both parts linked; with `TERM_PROGRAM=WezTerm` it showed only the text. So a link's URL may be nowhere on the screen.
- **vt100 keeps the link of each cell, like its colours** (our fork, used through `[patch.crates-io]` in Cargo.toml). Opening a link sets the one new text gets, closing clears it, and a cell holds a small id into the screen's table of links, so links scroll into the history with their text, and text drawn over a link replaces it. The table is bounded, as tmux's is (5000 links, 1 KB a URI): at most 4096 links and 1 MiB of URIs. When a new link doesn't fit, the ones no cell has are dropped, then the least recently used, whose cells lose them. That matters for Codex, which prints a URL again each time it grows while streaming, each a new link; Claude's `id=` is the same for the same URL across redraws and runs (recorded), so its redraws add nothing. A row also notes whether any of its cells may have a link (`Screen::row_has_hyperlinks`), so making room skips rows of plain text, and so does drawing. vt100 0.16 sent OSC 8 to `unhandled_osc`, which dropped it. Upstream vt100 is active again (0.17 and 0.18 in October 2026) but has no OSC 8, so the fork is five commits on top of its latest release (the `osc8-hyperlinks-0.18` branch; released builds up to 0.1.15 pin commits of the older `osc8-hyperlinks`). The OSC 8 change could be offered upstream, which would end the fork and the block on crates.io: not done, as publishing it needs the maintainer's OK. Until then taskman isn't on crates.io: a published crate can't depend on a git fork.
- **The fork also fixes erased cells** (upstream's `Cell::clear` stored the whole of the current attributes): with underline on, clearing the rest of a line left the blank cells underlined, so a pane drew an underline across blank space, and bold, italic, inverse and the foreground colour landed on blank cells the same way. xterm (back colour erase), Windows Terminal, kitty and Alacritty carry only the current background colour into cells they blank. The fork does too, for EL, ED and ECH and for the blank cells insert/delete character, insert/delete line and scrolling make, which upstream left with no colour at all. A unit test in `ui/pane.rs` draws `ESC[4m abc ESC[K` through tui-term and checks no cleared cell is underlined.
- **An earlier attempt, never merged, tracked links in taskman instead:** it split all output before vt100 at screen switches and pinned vt100's scroll position to count the rows its history took, about 690 lines in every session's output path, relying on undocumented vt100 behaviour. Output now goes to vt100 as before; keep it that way.
- **Drawing passes links on** (`links::mark`, as Codex does in its own TUI): after tui-term draws the session, each cell showing an http(s) link gets its symbol wrapped in OSC 8 and `CellDiffOption::ForcedWidth`, so ratatui counts the cell's width rather than the escapes'. A link's id goes along (when it's plain letters, digits, `-`, `_` or `.`), so the terminal underlines a wrapped link's cells together. The terminal then opens links itself: on the user's machine over SSH, and with taskman's mouse capture on, where ctrl+click inside taskman wouldn't have reached it in every terminal (macOS Terminal sends ctrl+click as a right click). While text is selected the pane draws a frozen copy, which carries no links.
- **Each link goes out once per run of cells** (`links::Runs`). Wrapping each cell on its own is the only way ratatui counts the cell's width right, but it sent the URL again for every cell, every time one was redrawn: a screenful of links in a 160x40 pane was 465 KB a repaint or scroll instead of 6–9 KB. The terminal's writer keeps a frame until ratatui flushes it, then leaves out each close that's followed by an opening of the same link with only cursor moves and colours between them (nothing printed, so the link stays open over them), as tmux and tcell send OSC 8 only when the link changes. That frame is now 9.3 KB; what's left is one opening and close per run. `mark` checks a link and builds its escape once per run too, and skips rows without links, so a session without links costs nothing to mark.
- **taskman doesn't set `FORCE_HYPERLINK`:** Claude decides on OSC 8 from the user's terminal's environment, which the pane passes on, so a terminal without links (macOS Terminal) still gets `text (url)` with the URL visible. Forcing it there hid URLs behind their text. A `FORCE_HYPERLINK` the user set passes through. On WSL with Windows Terminal, WSL doesn't pass `WT_SESSION` on unless the user lists it in `WSLENV`, so Claude printed plain text there and the OSC 8 path wasn't used at all (found while testing links there: a long `text (url)` broke at a `/` and only its first row opened). The guide's [Links on WSL with Windows Terminal](guide.md#links-on-wsl-with-windows-terminal) gives `export FORCE_HYPERLINK=1` first (Claude only, but right for Windows Terminal, which supports links), then `setx WSLENV "WT_SESSION:WT_PROFILE_ID"` for every tool. That takes effect only once Windows Terminal itself restarts, and it can keep running in the background (launch on startup, quake mode) after its windows close.
- **`prefix l` reads the links out of the cells** (`links::list`), newest first, once each: the screen and the history, a screenful at a time by scrolling the view, as the history in `$EDITOR` is read, each row once (about 35 ms for a 160-column, 10,000-row history). A link's text is joined across rows and the blanks between its parts; a text that is the URL, or its start, isn't shown as a label. Plain http(s) URLs in the text are found at the same time (`links::find_urls`, kept from that earlier attempt: up to a character a URL can't hold, less the punctuation that ends a sentence and a closing bracket the URL didn't open) and listed with the links, once each. Rows the terminal wrapped are joined, and so is a row whose text reaches the last column, without the next row's indent, since Claude breaks a word too long for the row itself. Both CLIs also break a long plain URL at a `/` or `-` on rows that aren't full; that can't be told from two lines of prose, so such a URL is found only in part. Nothing is tracked as output arrives. A full-screen CLI on the alternate screen keeps no history in vt100, so only its screen's links are listed.
- **Only http(s) is passed on or opened** (`links::openable`): the session decides the URL, and other schemes (`file:`, editor URIs, custom ones) can start programs. As in Codex, the URL must name a host. Others are listed, dimmed, and can be copied. A URL with whitespace or control characters isn't passed on, and one longer than 8 KB (Codex's limit; vt100 drops longer ones) isn't passed on or listed. tmux keeps 1 KB a URI; 8 KB stays so long signed URLs still open, and the table's 1 MiB budget bounds the memory either way. Text is cleaned (`untrusted::line`) before it's shown or copied.

## Links in panels

The tracker and GitHub panels, and the agents' project board, pass their links on as the session pane does: the issue (`App::issue_url`; Local files have no page), the PR, each check's run, reviews, review threads and comments, and http(s) URLs in descriptions, comments and reviews.

- **The same OSC 8 wrapping as the pane** (`links::mark_coded` shares `wrap` with `mark`): each linked cell's symbol inside OSC 8, with `CellDiffOption::ForcedWidth`, so anything drawn over a panel must `Clear` first too (the selection's corner label now does). The id is a hash of the URL (`id=taskman-…`), so a link wrapped over rows underlines as one.
- **Where a link landed is read back from a second render, not computed.** The panels are `Paragraph`s that wrap words and scroll, and the selection relies on their lines being drawn that way (`selection::Panel`). Rather than redo ratatui's wrapping, a panel's lines are built as a `links::Linked` (the lines, and which spans link where); the panel is drawn as before, then drawn again into a scratch buffer from `Linked::coded`: the same text, unstyled, each linked span coloured `Color::Rgb` by its URL's number. Wrapping and scrolling depend on the text alone, so every cell of the scratch buffer that holds a number is a cell of that link in the real one. The block's title goes through the same render, so the border can link too. A panel without links isn't drawn twice. The second draw and `mark_coded` cost about 0.15 ms a frame for a 60x40 panel with 21 links, 0.25 ms at 100x70 (measured when runs were added): small beside the session's own drawing, at most 60 frames a second, so it isn't cached.
- **The border's key or PR number links only while there's no title line** (`panel_head`): loading, or the fetch failed. Beside the title the second link added nothing, and it shares the title's URL and so its id: terminals underline a link's parts together, and the header lit up in two places on hover. taskman doesn't style these underlined; the terminal does, so not linking the span is the only way to drop it. The project board still links each key, which has no title beside it, and `prefix l` still lists the issue and PR first.
- **The URLs come from the data the panels already fetch:** the PR's details query asks for each check's `detailsUrl` (a status's `targetUrl`), and each review's, comment's and thread comment's `url`. The "N passed" line, when the passing checks are folded, opens the PR's checks page.
- **`prefix l` lists the ticket's links first** (`links::panel`): the issue, the PR, failing then running checks, reviews, unresolved threads, the comments shown, the URLs in all their text, then passing checks; then the session's links, newest first, without the URLs already listed. Each group has a heading when both are there. So everything a panel links is reachable from the keyboard, and in terminals without OSC 8.
- **Untrusted text**: titles, names and paths go through `untrusted::line`, bodies through `untrusted::clean`, before they're drawn or searched for URLs; only http(s) URLs with a host are linked (`openable`), as in the pane.

## Emoji that terminals measure differently

A warning sign with its emoji selector (⚠️, U+26A0 U+FE0F) is one column on its own and two with the selector, and terminals don't agree on what to do about it. Windows Terminal draws it two wide over whatever was in the second column; tmux 3.4 widens it on the selector but marks the column after the second as covered, so the second keeps its old character (3.5 fixed this); terminals that measure a character at a time draw it one wide and leave the second column alone. ratatui counts it as two and skips the second column, so whatever was there before (an overlay's border, a box the session redrew) could stay. ratatui 0.30 writes that column after the emoji, but crossterm's backend sends it without moving the cursor, so in a terminal that drew the emoji two wide it lands a column too far right, and so does the rest of the run.

taskman's `backend::Backend` writes a blank into that column first, then the emoji, each at its own position. Each terminal then shows the emoji with nothing stale beside it: drawn two wide over the blank, or one wide beside it, and tmux 3.4 is left as it is when a CLI prints the emoji directly. It does this only for a character whose first code point is narrower than the whole (a selector, a flag), which terminals measure differently, and only for cells the frame writes anyway, so the screen is never redrawn whole. Characters that are wide on their own (CJK, ✅) are left alone: every terminal clears the column they cover.

It works around a ratatui bug (seen in 0.30.2 with ratatui-crossterm 0.1.2: the diff yields x+1 after a U+FE0F cell, and the backend doesn't move the cursor after a two-column cell), and can go once a ratatui release fixes the backend's cursor position; `tests/emoji.rs` is the check. Until then it stays right if ratatui changes either half: the x+1 cell is covered by the emoji, so dropping it or never getting it loses nothing.

## Signals and panics

- SIGTERM, SIGHUP and SIGINT are counted by their handlers and end the event loop, which then takes the same way out as `ctrl+a q` (`shutdown` in src/main.rs): the terminal is restored, the heartbeat removed so commands queue, the state saved, every session stopped, and a worktree still being created or removed gets up to 30 s (`QUIT_WAIT`) to finish, since nobody is watching; `ctrl+a q` waits for it on screen instead, saying so, and then goes through the same shutdown. A second signal ends that wait at once, and a second SIGTERM or SIGHUP also has the watchdog end the process a second later, after removing the heartbeat, in case the loop is stuck. SIGINT is cleared after `$EDITOR` returns: in raw mode only `kill -INT` sends it, but ctrl+c at an editor that waits in cooked mode (`code --wait`) does too.
- **A closed terminal ends taskman, even when its loop is stuck.** Reading a closed terminal gives end of file, and crossterm 0.29 retries that forever inside its reader: `event::poll` would spin at a full core and never return, and the sessions would run on unattended. So the loop waits on the terminal itself (`Tty::wait`) and calls crossterm only when there's input. That doesn't cover a terminal that goes while crossterm is part-way through a sequence (a paste with no terminator, half a mouse report or key, as a dropped SSH connection can leave): crossterm reads on for the rest of it and spins again. A watchdog thread covers that and any hang not yet found: when the terminal has looked gone, or SIGHUP has come, for 3 seconds (`GRACE`; 30 s more once the shutdown runs, which may be waiting for git) and taskman is still running, it ends the process. The sessions' ptys close with it, which hangs up their CLIs. It needs the terminal gone at every check through the 3 seconds, since on macOS input read by the loop between `select` and the byte count looks like the end of file once. Patching crossterm's reader to stop at the end of file was the alternative; it would mean keeping a fork of crossterm, and it fixes only the hang that was found. The test (`tests/hangup.rs`) runs the binary in a pty and closes it mid-paste, mid-mouse report and mid-key.
- A panic in a session's pty reader (inside vt100, say) is caught: that session's CLI is killed, its pane says taskman stopped reading it and points to `panics.log` (the thread is named `reader <session name>`, so the log says whose it was), and the others go on. Its parser lock is poisoned, so every lock on a session goes through `session::lock`, which takes the guard anyway; the screen may be half-updated but stays drawable. The test hook (`TASKMAN_TEST_PANIC`) panics part-way through a buffer while holding the lock, as vt100 would, and tests/lifecycle.rs resizes, selects and draws that pane after it.
- A panic in a background thread that something waits on (a tracker fetch or PR lookup holding its panel's `loading`, git creating a worktree its session waits for, a form's check, a listing, a token read, `claude stop`, a look at a process tree, the keychain check, the updater) is caught too (`util::caught`, through `sync::Reporter` in the TUI). The thread sends the failure it would have sent for an error, saying taskman hit a bug and where `panics.log` is, and an error toast names what it was doing. Without that, the thread ended without a word and what waited for it waited for good: a panel never refreshed again, as `Remote::due` skips one still loading and `r` only asks for a refresh, and a session said "creating worktree" until restart. Threads that nothing waits on (a copy to the clipboard, the gh check, a tmux window) are left alone, and the quit's wait for removals and closed tickets' worktrees uses `is_finished`, which a panic ends too. Unit tests make the work panic (`App::panics`) with a payload their panic hook keeps out of the output.
- **An ended session keeps its screen.** A CLI's last words before it exits (an expired login, a refused resume id, a bad flag) are on the screen, so the pane goes on drawing it, with a banner saying how it ended (`session::End`: the exit code or signal, a start that failed, or the reader's panic) under the output, or at the top when the output reaches the bottom, as tmux's `remain-on-exit` and Zellij keep a dead pane. A start that failed has no screen: the pane says why, and when the program isn't there, what to do. Hiding the screen behind a fixed "has ended" made Enter repeat the failure without saying it.
- **A key typed after a resize arrives on its own.** crossterm 0.29 waits on the terminal and on its SIGWINCH pipe edge triggered, and when both are ready in one batch it reports the resize and drops the terminal's: the key stays unread until another comes, and the loop, which waits on the terminal level triggered, finds it readable at every pass and spins. So `Tty::wait` has a SIGWINCH pipe of its own and the loop reads crossterm as soon as it fires, while the resize is all there is, and also before it draws at a new size, so a key typed in reply to the redraw can't come with the resize. A key that still arrives in the same instant is held as before; after two passes that find input and read nothing, the loop waits out its 16ms instead of returning at once (`Tty::wait_held`), so it doesn't spin, and the next key brings both. Another zero-timeout poll can't get that key, as no new edge comes; the rest is crossterm's to fix. The test (`tests/resize.rs`) resizes a pty and sends one byte, once the frame at the new size is drawn: the frame before, kept at the bottom as its screen shrank, can look like it.
- **A frame is drawn when something on screen changed.** Every session's output used to set one flag that drew the whole screen, and the loop drew every 100 ms anyway: with the selected session idle and 9 others printing, that was about 54 frames a second, and idle it wrote about 210 bytes a second of frames that changed nothing. Now each session keeps its own flag (`Session::fresh`) and only the selected one's draws, at most every 16 ms (`FRAME`); the others' cards change with the 300 ms status poll, which sets `App::dirty` when it changes something, as keys, replies from threads (`Msg`) and toasts do. A resize draws at once, past the 16 ms, as nothing is on screen at the new size yet (with the selected session printing, the floor held a resize's frame back up to 17 ms, where before it took under 1 ms). A frame that showed a spinner asks for the next in 100 ms (`ui::animated`, set by `spinner` as it's drawn, so a spinner scrolled out of sight asks for nothing), and otherwise a frame comes once a second, for the ages and anything that changed without saying so. Which is due is `frame_due` in main.rs, from a `Due`. The readers wake the loop through a pipe in `Tty::wait`'s poll, beside the SIGWINCH one, so it waits up to 100 ms between passes (the threads' replies don't wake it) without the selected session's echo waiting; a reader writes to it only when its flag goes from clear to set, so a background session's output wakes it at most once per selection. The wait is rounded up to whole milliseconds (`whole_millis`): poll on Linux takes milliseconds and `filedescriptor` truncates, so the last millisecond before each frame was spent in polls that returned at once, about 1,000 passes a second with a spinner in sight, which doubled the main thread's CPU. The wakeup counts below didn't show that spin: they're voluntary context switches, and a poll that returns at once makes none, so count the loop's passes too when measuring it. A pointer moving with no button held is reported by the mouse mode but changes nothing, so it draws no frame (`redraws`). The terminal's escapes from the sessions and the poll (OSC 52, the bell, OSC 9) go out on the next pass, not with a frame. Measured with release builds in a 160x40 pty (medians of several runs), before and after: with those 9 busy sessions, 54 → 1 frames a second and 3.7% → 1.2% of a core (the rest is their screens' parsing); idle, 210 → 24 bytes, 9 → 1 frames and 56 → 10 wakeups a second. Working sessions show a spinner, so with one in sight it's 10 frames a second.
- **A frame is laid out from its own size.** The loop lays the screen out from the terminal's size each tick, and ratatui resizes the frame's buffer as it draws; a terminal that shrank in between (while a session spawned, say) would leave the session's pane and its links, which write into the buffer directly, indexing past it, and that panic on the main thread ends taskman and every session. So `ui::draw` lays out again from the frame (`App::lay_out`), and fits the session to it.
- The panic hook restores the terminal only on the main thread, whose panic ends the TUI. A worker thread's message would land in the middle of the screen, so it goes to `panics.log` in the state folder.

## UI choices worth keeping

- Projects are groups in one sidebar, not a separate rail: it costs no width (Claude needs about 80 columns) and keeps every ticket's status visible at once.
- Quiet states (idle, not started, ended and seen) show only a symbol (`○`, a grey `■`); words are kept for states worth a look: `▲ needs you`, `● your turn`, `⠋ working`, `+ new`, `■ exited`. `✦` marks an agent, so `new` has a glyph of its own. Help (`ctrl+a ?`) lists them all, from the same code the sidebar draws with.
- **States differ by shape, not only colour.** "Needs you" was a yellow `●` beside "your turn"'s green one, so in the collapsed sidebar, for colour-blind users and in some themes the state that blocks on you looked like the one that doesn't. It's `▲` now.
- **The badge is never cut; the name is.** The state is what the sidebar is scanned for, so it keeps its full width, right-aligned so badges line up, and the name gets what's left, cut at its end with `…` by display width (`util::truncate`, which never splits a wide character or an emoji from its selector). Shrinking the badge to its symbol when room ran short was considered and not chosen; showing symbols only is to be a setting instead.
- **The sidebar stays 30 columns.** Widening it for long agent names would take width from Claude on every screen; the Add and Rename forms suggest short names instead (about 12 characters fit beside a badge).
- **Form values never wrap.** A value wider than its field is cut with `…` at the end; while you edit it, it scrolls to keep the cursor in view, cut with `…` on either side, and moves only when the cursor would leave what's shown (`Field::view`), not on every key. A wrapped value used to run under the labels. Prose fields (an agent's Role) wrap under their value with a hanging indent, up to 4 lines, then scroll to the cursor's line.
- **A form taller than its window scrolls; its error and keys don't.** The Jira and Linear project forms take about 40 rows, so at 80x24 typing went into fields off screen, and the error that said why Enter did nothing was cut off too. The form scrolls to keep the focused field whole, with its section heading when there's room (`Form::view`, kept from frame to frame, so it moves only when the focus would leave the view, as `Field::view` does), and the error and key rows stay at the bottom of the pane, as Help's scroll line does. The approval dialog's role scrolls through the same `draw_scrolled`, by its keys rather than a focus. Below about 90 columns, Settings' form pane leaves too little beside its longest labels for values and hints, which wrapped to a few letters a row, so values and hints go under the label instead.
- **Text fields have a cursor, and ←/→ are its.** Branch's presets were cycled with ←/→, which is how text fields went without a cursor; they're a list under the field now, picked with ↑/↓ as the Ticket and Team fields pick theirs, except that Enter puts the preset in the field rather than saving, since a format is often a preset changed a little. Choices keep ←/→. The cursor is kept with the value it was placed in (`Field::caret`): values are set in many places (a pick from a list, a preset, a value filled in for you), and any change but the keys' puts the cursor at the end without each of them having to. It's on a grapheme boundary, so a wide character or an emoji moves and deletes as one. Words are letters and digits, so word moves stop at a branch's or a path's `/`, `-` and `.`; a token's go to its ends, since stopping at its punctuation would show where that is. ctrl+a stays the prefix: Home goes to the start. Hints wrap the same way. Settings measures the form at the width it draws at, key line included, or wrapped hints push the keys out of view.
- **Account pickers show a short label and keep the id.** `who · short source` (`cmd:op`, or `env:NAME` in full), since a password-manager command is wider than the field; two accounts that would look the same show their whole sources cut in the middle, where commands usually differ. Saving reads the account's id kept beside each choice, never the label, which can now collide.
- The footer is a full-width bar, like tmux's status line. On screens 30 rows or taller a blank row separates it from the panes, whose last rows and borders looked cramped against it; shorter screens keep that row for Claude.
- Settings is one popover listing updates, projects and accounts, so every project is reachable, including ones without tickets.
- Agents show a project board on the right, with what the sidebar can't carry: why a ticket needs you (Claude's own message), its branch, failing and running checks by name, the latest review and the latest comment. A first board only repeated the sidebar; giving agents the full width instead made Claude's text too wide to read comfortably. Both were tried.

## Distribution

Releases are prebuilt binaries for macOS (arm64, x86_64) and Linux (x86_64, arm64; each with glibc and with musl), built by a GitHub Actions workflow on version tags; the workflow can also be started by hand for an existing tag, which `scripts/release.sh` does when the tag push doesn't start it. WSL uses the Linux build. `taskman update` checks the latest release and installs it into the running binary's own folder, so it updates in place wherever it was installed (a development build in `target/` and a Homebrew install are refused).

A release can't be taken back: releases are immutable, and every install updates to the latest within the hour. So nothing is published until CI on `main` has passed on the tag's commit (the workflow waits for it, as the release script pushes the commit and its tag together, and the script itself waits for CI on the commit it bumps), and each binary has run on its runner and said the tag's version. The required checks alone aren't enough: an admin's push to `main` skips them, and one release went out before CI on its commit had finished. A CI run started by hand on `main` counts as well as a pushed one: GitHub has dropped push events for merges and left a finished run "in progress" for hours, and with pushed runs only, neither could be got past. Both gates read the run's conclusion, so the coverage job, a report whose `cargo test` has no rerun for a flaky test, can't fail it (`continue-on-error`). CI on `main` runs once per commit (its concurrency group is the commit), as a group per branch let a third push cancel the run waiting behind the second. During GitHub incidents a run has also flapped in and out of the list of runs, and stayed "in progress" for two hours after all its jobs had passed, so both gates take a missing answer after a run was seen as no news, and pass a run whose jobs all passed ten minutes earlier; the workflow's gate, when it does give up, can be re-run on its own (`gh run rerun <run> --failed`), keeping the builds. A tag push GitHub delivers minutes late, after the release script has started a run by hand, starts a second run: the runs for a tag queue (`queue: max`, as the default queue of one would cancel a third), and one that finds the tag released builds nothing and ends green rather than failing or being cancelled, either of which marks the release commit red. The release script pushes main and the tag atomically, as a tag that lands without main is a protected tag on a commit off `main`, and it runs no tests itself: CI tested the same code, and a flaky terminal test on a busy machine failed a release CI had passed. The Intel macOS binary runs through Rosetta on the Apple Silicon runner; where Rosetta is missing, only that binary goes unrun. The builds use the Rust in `rust-toolchain.toml`, the one CI tests with, rather than whatever the runner image carries, and the `dist` profile: fat LTO and one codegen unit, which cut the Linux binary by a fifth (7.8 MB to 6.0 MB in a local build) for a build nearly twice as long (77 s against 44 s), in a profile of its own so `cargo build --release` stays quick. It keeps symbols: stripping them would save another 0.75 MB, but a backtrace in `panics.log` (with `RUST_BACKTRACE=1`) would then name no functions. `panic` stays `unwind`, as a session's reader thread survives a panic in the terminal parser through `catch_unwind`.

Releases are downloaded over HTTPS from the repository's release pages, which need nothing installed, the repository being public: the latest tag is where `releases/latest` redirects, not the REST API, which allows 60 unauthenticated calls an hour per address. `gh` is the fallback, for a private copy of the repository, whose pages need a login. A request whose connection drops is asked once more before gh is tried, and no connection is kept between requests: ureq reuses one after a response that has a length, even from an HTTP/1.0 server that is about to close it, which made `scripts/test-install.sh` flaky in CI. The owner and name live in Cargo.toml's `repository` (the code reads `CARGO_PKG_REPOSITORY`) and in one variable in `scripts/install.sh`, which runs on its own. Each release has one `SHA256SUMS`, written by the release job, and an install with no checksum, or one that doesn't match, installs nothing: a check that can be skipped checks nothing. The new binary must also run and report the release's version before it is renamed over the old one, so a bad build leaves the working one in place. The checksum comes from the same release, so it catches broken and truncated downloads, not a compromised release; the release workflow is what guards that: its build jobs, which run every dependency's build script, get a read-only token that isn't kept in `.git/config`, only the release job can write, and actions are pinned by commit.

An attestation shows who built an archive, which the checksum can't: the release job signs a statement for each file (`actions/attest-build-provenance`, which needs a public repository), and `gh attestation verify <archive> --repo <owner/name> --cert-identity-regex '^https://github\.com/<owner>/<name>/\.github/workflows/release\.yml@refs/(tags/v[0-9]+\.[0-9]+\.[0-9]+|heads/main)$' --deny-self-hosted-runners` checks that the release workflow made it, run from a version tag or main (where `scripts/release.sh` starts it by hand for a tag), on GitHub's runners. `--repo` alone would accept any workflow in the repository; only the release job may attest today, but pinning the workflow keeps it that way if another workflow is ever given the permission. `--signer-workflow` pinned the workflow but not the ref it ran from, and the workflow can be started by hand on any branch, so a branch's edited copy could have signed; gh won't take it with `--cert-identity-regex`, which checks both. `SIGNER_REFS` in `src/update.rs` and `signer_refs` in `scripts/install.sh` are the same (a unit test keeps them so), and `scripts/test-install.sh`'s fake gh refuses a call without the identity or `--deny-self-hosted-runners`. gh needs the archive in a file: taskman writes it into a new folder of mode 0700, created rather than reused, and the install script into its `mktemp -d` folder, so no other user can swap it between the checksum and gh or plant a link at its name. The install script, `taskman update` and the background updater run it once the checksum matches, the updater through `proc::run` with a time limit on its own thread. The install deliberately doesn't need gh, so gh missing, logged out (it exits with 4, or GitHub answers 401) or too old to have the command falls back to the checksum, and so does a release from before v0.1.0 with no attestation (`no attestations found`, or a 404 from a private repository); `taskman update` and the script say so. The background updater doesn't fall back: it leaves such a release to `taskman update` (below). Anything else gh says, a timeout included, refuses the archive: those cases are recognised by gh's words, and a fallback for words it doesn't recognise would let any failure through. A network that blocks GitHub's API or Sigstore would then block every update for someone with gh, so `TASKMAN_INSECURE_SKIP_ATTESTATION=1` skips the check, loudly: `taskman update` and the script print a warning, and Settings says it's set. The refusal names the variable only when gh's error could be the network (a timeout, a connection or TLS error, HTTP 5xx, 429 or a rate limit), and never next to gh's verdict on the archive (its signature, signer or digest), which is checked first: a message that suggests turning the check off right when it caught something would undo it. A missing attestation can't simply be a fallback: a replaced archive has none either, and would install on its checksum like an old release. So `REQUIRE_ATTESTATION_FROM` in `src/update.rs` and `require_from` in `scripts/install.sh` (a unit test keeps them equal) name the first release that must have one, v0.1.0, the first built on the public repository: a release from then on without one is refused when gh can check, and only the v0.0.x releases from before still fall back. Immutable releases keep a published release's files from being replaced at all. The switch is a constant, not a setting: anything that could turn it off at run time would turn it off for whoever replaced the archive too. So `scripts/test-install.sh` covers both sides with what it controls: for the install script, copies with `require_from` rewritten (empty, or a fake release's tag); for `taskman update`, whose binary has the constant compiled in, fake releases on each side of it, one from before and the first that must have one.

The TUI also updates itself, the way Claude Code does: it checks at every start and every hour, installs a newer release in the background, and the sidebar says it applies on restart. Installs fell behind when updating took remembering a command. The background takes less than `taskman update` does, as nobody is there to read what it checked: only a release whose attestation gh verified (`accepts`), so a release published with a stolen token, whose checksum matches its own `SHA256SUMS`, isn't installed on every copy without gh within the hour; and only one with the same major and minor version (`same_minor`), as a new minor is a breaking release before 1.0 and would change keys, config or saved state without a word. Those get a notice instead: `↑ vX.Y.Z: run taskman update` when it couldn't verify (Settings → General → Updates says why), `↑ vX.Y.Z: breaking changes` for a new minor, with its notes linked in Settings. When gh isn't installed or the check is skipped, it says so without downloading the archive first. It never restarts by itself: a restart is cheap (sessions resume), but only between the user's turns, so the user picks the moment. The install writes a file beside the binary and renames it over, so the running TUI keeps its copy and a hook never runs a half-written file. Sessions' hooks and `taskman status` run the binary's path, so after an install they run the new release while the old TUI is still up: the status file format must stay readable across releases (a test pins it), which the versioning rule already treats as breaking to change. The binary installs a release itself rather than piping a script into bash, so the release assets' names (`taskman-<tag>-<target>.tar.gz` with `taskman` at its top level, and `SHA256SUMS`) are what must stay stable; the oldest updaters instead run the new release's `scripts/install.sh` through `gh`, which keeps their environment variables working. Development builds, `cargo install` copies (cargo manages that folder), Homebrew installs and folders taskman can't write to only show the notice. A start always checks (one request, and starts are rare), so a restart picks up a release at once; a first version skipped the check when the last one was under 6 hours old, and a release took hours to show. `update.json` in the state folder keeps what was found and installed, so the notice outlasts a restart and a running TUI notices `taskman update` runs.

`taskman uninstall` removes taskman as `rustup self uninstall` does, but keeps the user's data unless asked, as `apt remove` does and `apt purge` doesn't: a reinstall then picks up the projects, accounts and tokens, and removing a program shouldn't cost a person their setup by default. `--purge`, or yes to the second question, removes the data and the tokens together, never one without the other: tokens kept for accounts that are gone are secrets nobody can find, and accounts kept without their tokens fail on the next start. It removes only the program `taskman update` would replace (`update::installs`): a cargo, Homebrew or development copy, or one in a folder taskman can't write to, was put there some other way, so it's left with a word on how to remove it rather than removed behind its manager's back. The running program removes its own file last; Linux and macOS both keep a running program's file until it ends, so that's safe. It removes only taskman's own paths, and of the token files only those in its own token folder that its accounts read, never a file a `cmd:` names elsewhere. A link where one of those paths should be is refused rather than followed or removed (the user may keep `~/.config/taskman` in a dotfiles repository), and `remove_dir_all` removes the links inside a folder, not what they lead to. Links above those paths are the user's layout (macOS's `/var` is `/private/var`, and a home folder may be reached through one), so paths are compared with the links above them resolved and the last part as it is: the program's path comes back resolved from the system while `$HOME` may not be, and a token file saved when the config folder was spelled another way is still found in taskman's token folder. Repositories, worktrees, branches, shell startup files and the CLIs' folders are the user's: it lists the worktrees taskman made and the lines the user may have added, and touches none of them. It refuses while a TUI runs, whose sessions would carry on and whose next save would write the state back, and isn't on the sessions' allow-list, so a session can't run it unasked.

Each archive carries `LICENSE-MIT`, `LICENSE-APACHE` and `LICENSE-THIRD-PARTY` beside the binary. The crates built into it are under MIT, Apache-2.0 and similar licenses, which ask for their notices to go with the binary, so the notices are a condition of distributing it, not a courtesy. The install script and `taskman update` take only `taskman` out of the archive (a bin folder is no place for license files), so the binary embeds the notices too and `taskman --licenses` prints them: an installed copy carries them however it was installed. cargo-about generates the file from `Cargo.lock` (`about.toml` accepts the licenses `deny.toml` does, `about.hbs` is the layout), and it's committed, as `include_str!` needs a file: the embedded and the archived copies are then the same file. CI regenerates it and fails when it differs, so a dependency change comes with the file, and the release build does the same before packaging and refuses a tag where it's stale, so a release never ships notices that don't match its lockfile. The file names the crates but not their versions, so a bump that changes only versions, as most of Dependabot's do, leaves it as it is and passes CI without anyone regenerating it; a crate built in at two versions is listed twice. The Linux glibc binaries need glibc 2.34, the highest `GLIBC_` version `objdump -T` lists on them. install.sh's `glibc_min` says so, the docs state it, and the release build refuses a binary that asks for a newer one, as install.sh would then hand it to machines it doesn't run on: after a toolchain or runner change that raises it, raise `glibc_min` and the docs with it.

Linux has a glibc and a musl build for each architecture. The glibc one is what most machines get, and what x86_64 installs had before the musl one existed; the musl one is static, so it runs where glibc is missing (Alpine) or older than the glibc build needs. install.sh picks between them by `getconf GNU_LIBC_VERSION`, which glibc's getconf answers and musl's doesn't, against `glibc_min`. `taskman update` doesn't look again: a copy updates to the build it is (`target_env` at compile time), so an install stays on its archive, and a glibc copy already runs where it is. The arm64 builds run on GitHub's arm64 runners (free for public repositories), so every Linux binary is run on its own architecture before release. No build is optional: releases are immutable, so a release published without one archive could never get it, and the machines install.sh and `taskman update` send to that archive would find none. A failed build leaves no release, and the release job checks there's an archive for each build install.sh picks before it publishes. A dry run of the workflow (`-f dry_run=true`, from a branch) builds and checks them all without a tag and publishes nothing, so a new build can be tried on GitHub's runners before a release depends on it. There's no native Windows build: hooks, `cmd:` tokens and paths assume a Unix shell. Binaries aren't signed for macOS; downloads through curl, `gh` or taskman itself aren't quarantined, so they run without it.
