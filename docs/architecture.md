# Architecture

A map of the code for anyone changing it, people and coding agents alike: what's where and how the parts talk. Why things are built this way is in [design.md](design.md); what taskman does for its users is in the [guide](guide.md). Keep this file current in the same pull request when files or structure change.

## Bird's-eye view

taskman is a Rust terminal UI for working on several tickets at once. A project is a folder (usually a repository) with its sessions: real `claude` (or `codex`) CLIs in embedded terminals. Project agents are sessions with no ticket that can message the others. Integrations are optional and per project: a tracker (Jira, Linear, GitHub Issues or Local files) adds tickets, each with a tracker panel and usually its own worktree, and a GitHub remote with `gh` adds a PR panel.

One thread draws the screen and feeds every session's terminal; everything slow (trackers, `gh`, git fetches, token commands) runs on plain threads that report back over a channel. The same binary is also the command line the sessions use (`taskman status`, `add`, `close`, `move`), the hook Claude Code and Codex run (`taskman hook`), and the way a session moves to another terminal (`taskman resume`). Saved state is two JSON files: `tickets.json` in the state folder (`~/.local/state/taskman/`) and `config.json` (accounts and settings).

## Code map

### Entry point and commands

| File | What it holds |
|---|---|
| `src/main.rs` | entry point, terminal setup (mouse, bracketed paste, kitty keyboard flags), event loop (`Tty::wait`, which wakes on input, a resize, a session's output, a thread's reply or a signal that quits; `frame_due`, when the next frame is due; `wait_for`, how long to wait for one or the next tick), the shutdown every quit goes through (`shutdown`: heartbeat, save, sessions, and after a signal a bounded wait for git), the watchdog that ends taskman when the terminal is gone or a second signal comes, the `hook`, `status`, `add`, `close`, `move`, `resume`, `update`, `uninstall`, `--version`, `--licenses` and `--help` subcommands, handing the terminal to `$EDITOR` |
| `src/cli.rs` | what the CLI commands share: how one runs (`run`: `--help` before anything else, then its error or exit code) and prints (`out!`, which a reader that stops early, as `| head` does, doesn't turn into a panic), the lexer that reads every command's arguments alike (`Lexer`: `--x`, `--x VALUE`, `--x=VALUE`, an empty value, an unknown option with the command's usage), the project a command means (`pick_project`, `project_named`, `context`), keeping a session to its own (`session_project`, `confine`), and the key an input names in it (`resolve_key`) |
| `src/coding_cli.rs` | everything that depends on the coding CLI a session runs (`store::Cli`), as one method each: its program and the variable that overrides it, its arguments (`args`, and a fork's first launch: `fork_args`, `chooses_fork_id`, `min_fork_version`, `probe_fork`), hooks (`hooks`: `--settings` for Claude, `-c` overrides for Codex), transcripts (`home`, `has_conversation`), the keys that answer its permission prompts, who the screen shows answering an approval (`reviews_approvals`, `approver`: Codex's reviewer or the user), whether the screen shows it asking to trust its folder (`asks_trust`), the key that opens its full transcript (`transcript_key`), and what its sessions can do (`messages_agents`, `sandboxed`, `runs_in_background`, `switches_conversations`) |
| `src/status.rs` | `taskman status [KEY]`: a ticket's issue, worktree and PR fetched fresh, an agent's project overview with session states, or from a plain shell whichever the current folder belongs to (else every project, a line per ticket); the briefs point sessions here |
| `src/add.rs` | `taskman add KEY...`: picks the project and key, checks the key with the tracker (or creates the ticket there, `--new` from a shell; from a session it asks the TUI to, once the user approves), leaves a request in the inbox folder and prints the TUI's reply; also the TUI's side of the inbox (claiming requests, replying, the `alive` heartbeat) |
| `src/close.rs` | `taskman close KEY...` / `--merged`: finds each ticket's project, sends a close request through the inbox and prints the reply; the TUI's per-ticket outcome, its reply line and the worktree removal it runs (`remove_worktree`) |
| `src/resume.rs` | `taskman resume KEY`: continues a ticket's or agent's session in the user's terminal with `App::launch`; the owner file whose lock keeps a session to one copy (pane or outside) |
| `src/hook.rs` | `taskman hook <state>`, run by the Claude Code hooks taskman installs; writes status files (each record naming the start of the session it belongs to) and refresh signal files, and each finished turn to the session's log (`log_turn`: the commit a prompt starts on and the files each edit names, noted as they come, then, after the status record, a line at Stop with the turn's commits and the files they changed, less what the default branch has: `made_since`; all in the session's own folder, `TASKMAN_CWD`) |
| `src/events_log.rs` | a session's log beside its status file (`<KEY>.events.jsonl`): a JSON line per finished turn (`Turn`: the CLI's last message, the files edited, the commits), appended, and written again with the newest `KEEP` once it holds twice as many; readers skip a line that isn't JSON or is another `kind`, and read odd fields as defaults; the turn under way's scratch file (`Pending`, `<KEY>.turn.jsonl`; a Stop leaves the commit it ended on there for a Stop that follows with no prompt), and the files a tool call edits (`edited`: Claude's Edit and Write tools, Codex's apply_patch, as its own tool or a command its shell tools run) |
| `src/status_file.rs` | the status record the hooks write and the TUI, `taskman status` and `taskman resume` read (`Record`, `read`, `write`): every field may be missing or odd, an unknown state reads as idle, and the file is written byte for byte as before the struct; the words for each state (`HookState::word`) and the names of running sessions (`running_names`) |
| `src/update.rs` | `taskman update`, and the TUI's background updates (`Updater`): finds the latest release, downloads it over HTTPS (`gh` as the fallback, for a private repository), checks its SHA256SUMS, its attestation when `gh` can (`gh attestation verify` on a copy in a private folder, signed by the release workflow from a version tag or main on a GitHub-hosted runner; `TASKMAN_INSECURE_SKIP_ATTESTATION` skips it), and that it runs; in the background only a release of the same minor version whose attestation verified (`to_install`, `accepts`), renames it over the running binary, keeps `update.json`, and says what the sidebar shows |
| `src/uninstall.rs` | `taskman uninstall`: refuses while a TUI runs (the inbox heartbeat, then the state folder's lock, held to the end), lists what goes and what stays, and asks (`--yes` and `--purge` answer for it); removes the program when `update::installs` says it's the install script's copy, last, and with `--purge` the config and state folders, the keychain items its accounts name and the token files in its own token folder (`plan`, `remove`); refuses a link where one of its own paths should be (`own`), never follows one inside them, compares paths with the links above them resolved (`resolved`, `tilde`), and lists the worktrees taskman made that are still there |

## How the pieces fit

- **Sessions.** `App::launch` (used by the pane's `build_command` and by `taskman resume`) starts `claude` with `--name <key>` (`<project>/<key>` while another project has the key: `store::session_name`; other sessions message it by that name), `--resume <id>` when a transcript exists, `--append-system-prompt` (the ticket or agent brief), and `--settings` adding hooks that run `taskman hook <state>`. Hooks write `~/.local/state/taskman/status/<project-id>/<KEY>.json` (`store::status_file`), which `poll_status` reads, and add each finished turn to the log beside it (`events_log`), which only closing the ticket or agent removes (`remove_status_files`; a start of the session or of taskman clears the status file alone); each start passes `TASKMAN_LAUNCH`, which the hook records, so a hook of an earlier start writing late isn't taken for the running session's (`TicketView::takes`). A ticket is its project's main checkout and its key (`Ticket::is`): keys repeat across projects, so never look one up by key alone. The user's own Claude settings are never touched. A ticket with `cli: Codex` starts `codex` instead (`Cli::args`): the same hooks as `-c` overrides with their trust hashes (`hook::codex_config`), the brief as `developer_instructions`, and `codex resume <id>`. Sessions get a `taskman` link to the running binary first on their PATH, and the briefs tell them to read their ticket with `taskman status`. The `--settings` permissions allow `taskman status`, `taskman add` and `taskman move` without a prompt (`hook::settings_json`), and in a session the three refuse any project but its own, the one in `TASKMAN_REPO` (`cli::confine`), since the rules can't tell arguments apart; an agent or role from `taskman add`, and a ticket a session's `taskman add --new` asks for, still waits for the user's approval in the TUI. Text from trackers and PRs is untrusted: print it through `untrusted` and keep it out of briefs (see "Untrusted text" in [design.md](design.md)). Agents add tickets and other agents with `taskman add`, which leaves a request in the state folder's `inbox/` for the TUI (`take_inbox`) rather than editing `tickets.json`. A change to the request needs a new `add::INBOX_FORMAT`, so a command never asks an older running TUI for something it can't do. An agent's optional `role` (`Ticket::role`, kept on `ClosedAgent` too) is appended to its brief at every session start. Agents added through `taskman add` start their session once the user approves them (`App::ask_next`, then `TicketView::start`); a session's new ticket (`add::Item::New`) is created on a thread once approved (`App::answer_new`, then `Msg::Created`) and added like any key. `taskman close` uses the same inbox (a request with `close`); the TUI closes through the close dialog's code (`App::close_at`, then the removal check) and it's deliberately not on the allow-list.
- **Handed-off sessions.** `ctrl+a t` and `taskman resume` move a session between the pane and the user's terminal; `TicketView::away` says where it is, and `resume::Hold` (an `flock` on `<KEY>.owner` beside the status file) keeps it to one copy. Never start a session without `start_session`, which takes that lock.
- **Stopping sessions.** A stopped CLI takes a moment to go (hung up, then killed, on a thread): until it's reaped, the ticket's `reaper` (`TicketView::stop_session`) keeps a new session from starting, a closed ticket's worktree from being removed and, after a hand-off, the claim from being let go, the owner file reading `Owner::Stopping` meanwhile. See "Stopping a session" in [design.md](design.md).
- **Stacked tickets.** `Ticket::base` names the ticket a worktree started from; whether it merged comes from the base ticket's PR or from the ticket's own PR's `baseRefName` (`App::stack_of`).
- **Background work** runs on plain threads and reports back over an `mpsc` channel (`Msg`); there is no async runtime. `Remote<T>` holds fetched data with its freshness and refresh flags. Keep network calls and token commands off the UI thread; commands go through `proc::run` so a hung one gives up.
- **Accounts vs projects.** An account is credentials (`store::Account`, id like `jira-1`); a project's tracker names its account or falls back to `Config::account_for`. Tokens are never stored: `env:VAR`, `cmd:COMMAND` or `keychain:NAME`, read in the background by `tracker::Clients`. The account form can write a pasted token to the keychain first (`keychain::Keychain::store`), or where there's none to a private file read by a `cmd:cat` (`token_file::store_in`), in its background check.
- **Trackers.** Fetching goes through `tracker::Client`, and each difference between providers is a method on `Provider` or `Tracker` in `tracker.rs` (`needs_account`, `has_board`, `branch_source`, ...): use those rather than matching on a provider. The account forms are built from them too: the providers offered are those that `needs_account`, and each one's rows come from `signs_in_with_email`, `account_site_hint`, `email_hint`, `token_var` and `token_page`. A new provider is a `store::Provider` variant, its API module, a `tracker::Client` variant and one arm per method in `tracker.rs`.
- **Coding CLIs.** Each difference between Claude Code and Codex is a method on `Cli` in `coding_cli.rs`: use those rather than matching on the CLI or comparing with `Cli::Claude`. A new CLI is a `store::Cli` variant and one arm per method; the briefs build their text from the capabilities (`messages_agents`, `sandboxed`), so a CLI that gains one gets its text.
- **Modes.** `Mode` decides where keys go: Claude (Normal), a form, Settings, or a confirm dialog. Every key goes to Claude except after the prefix (`ctrl+a` unless changed). Hints name it through `keys::prefix()`, never a literal `ctrl+a`.

## Invariants

What must stay true whatever changes. Each has a section in [design.md](design.md) saying why.

- **A ticket is its project and its key** (`Ticket::is`). Keys repeat across projects, so nothing looks a ticket up, names its status file or claims its session by key alone. An agent is found by its project and name (`Ticket::is_agent`, `store::find_agent`), not by a key made from the project's name: `store::agent_key` makes the key only when an agent is added or renamed, and a renamed project keeps its agents' keys.
- **One copy of a session.** Every session starts through `start_session`, which takes the owner lock (`resume::Hold`); a pane and `taskman resume` never run the same session at once, and a lock that can't be taken stops the session starting. The lock is taskman's, not the CLI's, so a session also starts only once the last one's CLI is reaped (`TicketView::reaping`), and a hand-off keeps the lock until then. `taskman resume` finds sessions in the saved state, so a rename, close or project removal saves first (`App::try_save`) and is undone when the save fails, its claims kept.
- **A session runs in its own folder or not at all.** `start_session` and `taskman resume` refuse when the folder is gone (`Gone::of`), as portable_pty would run the CLI in the home folder instead.
- **One conversation per session.** `session_ids::claim` refuses an id another ticket or agent holds, wherever an id comes in.
- **The user's own CLI settings are never touched.** Hooks and permissions come in through `--settings` (Codex: `-c` overrides) on each launch.
- **Tracker and PR text is untrusted.** It's printed through `untrusted` and never goes into a brief, since anyone who can write a comment could write instructions.
- **Tokens are never stored.** Accounts say where a token comes from (`env:VAR`, `cmd:COMMAND` or `keychain:NAME`); it's read in the background when needed. A token pasted into the account form lives in the form only until it's in the keychain, or in a private file whose `cmd:cat` the account saves.
- **Nothing slow runs on the UI thread.** Network calls and token commands run on threads; git, gh and token commands go through `proc::run`, with a time limit and no terminal.
- **Saved state is never replaced by less.** Only a missing file reads as empty; a file this build can't read, or of a newer `store::FORMAT`, stops the TUI rather than being overwritten. New fields get `#[serde(default)]`; fields a build doesn't know are kept in each struct's `extra` and written back, and code that rebuilds a saved struct carries its `extra` over.
- **Sessions change the TUI's state only through the inbox.** `taskman add` and `taskman close` leave requests for the running TUI instead of editing `tickets.json`; a changed request gets a new `add::INBOX_FORMAT`.
- **Provider differences live in `tracker.rs`,** as methods on `Provider` or `Tracker`, not as matches on the provider elsewhere; **CLI differences live in `coding_cli.rs`,** as methods on `Cli`.

## Cross-cutting concerns

- **Threads and messages.** There is no async runtime. Background work runs on plain threads and sends a `Msg` over an `mpsc` channel; `drain_messages` applies them on the UI thread each tick. `Remote<T>` (in `app/sync.rs`) is fetched data with its freshness and refresh flags, so a ticket never starts a refresh while one is in flight, and the id of its latest fetch, so a reply that lands after the tracker changed or the ticket was closed and added again is dropped rather than shown as fresh. A thread whose message something waits for starts through `Reporter` (`App::reporter`), which catches a panic in its work and sends the failure instead, with an error toast pointing to `panics.log`.
- **Status files and hooks.** A session's state comes from the files its hooks write under the state folder's `status/<project-id>/`, read by `app/poll.rs`; each record names the start of the session that wrote it, and the pane takes only its own start's. When no hook fires (an approved permission prompt, an interrupt), or a Codex approval request's hook fires before its reviewer decides, the state is inferred from keys and the screen.
- **The owner lock.** `<KEY>.owner` beside the status file, held with `flock` by whichever process runs the session (the TUI or `taskman resume`), by the TUI after a hand-off until the pane's CLI is reaped, and by the git removing its worktree; the system releases it however the process ends. A closed ticket's file is removed with its status files and saved history (`poll::remove_status_files`), or by the close's own hold as it lets go (`Hold::closing`); `take` retries a file removed under it. It's taken before every start and fails closed: without it, the session doesn't start.
- **The inbox.** The state folder's `inbox/` carries requests from the CLI commands to the running TUI and the TUI's replies back; `inbox/alive` is the TUI's heartbeat (written whole and renamed into place, so a command never reads it half written) and says which request formats it understands, so a command knows what it may ask; whether anything will answer is the state folder's lock while `alive` is there (`add::tui_running`), since the file's age is read on the wall clock, which can step; it also names the TUI's pid and machine, which refuse a second TUI whose lock the first doesn't hold (`add::before`): the pid is checked only on the same machine.
- **Text width.** What's drawn is measured in the columns ratatui gives it, grapheme by grapheme (`util::width`, through ratatui's own `CellWidth`): a CJK character or an emoji with U+FE0F takes two, a combining mark none, a control character none, as ratatui leaves those out. Every cut (`util::truncate` and its kin, `wrap_words`, the forms' `wrap_prose`), pad and right-aligned column is measured with it, and cuts keep whole graphemes, so a wide character or an emoji's selector is never split. `chars().count()` and `format!`'s `{:<n}` count characters, and a CJK title cut by them ran past its room, losing its `…` and pushing right-aligned counts out of view. Untrusted text goes through `untrusted` before it's measured.
- **Testing layers.** Unit tests sit next to the code; pure decisions (parsing, matching, ordering) are extracted so they can be tested where they live. Code that parses others' text has `proptest` properties too. `app/test_support.rs` builds an `App` on a mock project with nothing started; `app/events/` drives it with keys, mouse reports, pastes and messages; `ui/screens.rs` compares what's drawn with `insta` snapshots. The tracker clients are tested against recorded responses in `tests/fixtures/`, served by `replay.rs` (GitHub Issues' by its test runner); no test reaches a real tracker or runs gh for one; the PR lookup's unit tests pass `fetch` a gh that answers from the same fixtures. What needs the real binary (the terminal, signals, a CLI's process, hooks, the clipboard and browser commands) is in `tests/`, which runs it in a pty with stub CLIs, its own home, and stubs for gh and the keychain tools first on PATH, so no test reaches the developer's own login or keychain.
