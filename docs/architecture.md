# Architecture

A map of the code for anyone changing it, people and coding agents alike: what's where and how the parts talk. Why things are built this way is in [design.md](design.md); what taskman does for its users is in the [guide](guide.md). Keep this file current in the same pull request when files or structure change.

## Bird's-eye view

taskman is a Rust terminal UI for working on several tickets at once. A project is a folder (usually a repository) with its sessions: real `claude` (or `codex`) CLIs in embedded terminals. Project agents are sessions with no ticket that can message the others. Integrations are optional and per project: a tracker (Jira, Linear, GitHub Issues or Local files) adds tickets, each with a tracker panel and usually its own worktree, and a GitHub remote with `gh` adds a PR panel.

One thread draws the screen and feeds every session's terminal; everything slow (trackers, `gh`, git fetches, token commands) runs on plain threads that report back over a channel. The same binary is also the command line the sessions use (`taskman status`, `add`, `close`, `move`), the hook Claude Code and Codex run (`taskman hook`), and the way a session moves to another terminal (`taskman resume`). Saved state is two JSON files: `tickets.json` in the state folder (`~/.local/state/taskman/`) and `config.json` (accounts and settings).

### Entry point and commands

| File | What it holds |
|---|---|
| `src/main.rs` | entry point, terminal setup (mouse, bracketed paste, kitty keyboard flags), event loop, the shutdown every quit goes through (`shutdown`: heartbeat, save, sessions, and after a signal a bounded wait for git), the watchdog that ends taskman when the terminal is gone or a second signal comes, the `hook`, `status`, `add`, `close`, `move`, `resume`, `update`, `--version`, `--licenses` and `--help` subcommands, handing the terminal to `$EDITOR` |
| `src/cli.rs` | what the CLI commands share: how one runs (`run`: `--help` before anything else, then its error or exit code) and prints (`out!`, which a reader that stops early, as `| head` does, doesn't turn into a panic), the lexer that reads every command's arguments alike (`Lexer`: `--x`, `--x VALUE`, `--x=VALUE`, an empty value, an unknown option with the command's usage), the project a command means (`pick_project`, `project_named`, `context`), keeping a session to its own (`session_project`, `confine`), and the key an input names in it (`resolve_key`) |
| `src/status.rs` | `taskman status [KEY]`: a ticket's issue, worktree and PR fetched fresh, an agent's project overview with session states, or from a plain shell whichever the current folder belongs to (else every project, a line per ticket); the briefs point sessions here |
| `src/add.rs` | `taskman add KEY...`: picks the project and key, checks the key with the tracker (or creates the ticket there, `--new`), leaves a request in the inbox folder and prints the TUI's reply; also the TUI's side of the inbox (claiming requests, replying, the `alive` heartbeat) |
| `src/close.rs` | `taskman close KEY...` / `--merged`: finds each ticket's project, sends a close request through the inbox and prints the reply; the TUI's per-ticket outcome, its reply line and the worktree removal it runs (`remove_worktree`) |

| `src/hook.rs` | `taskman hook <state>`, run by the Claude Code hooks taskman installs; writes status files (each record naming the start of the session it belongs to) and refresh signal files |
| `src/status_file.rs` | the status record the hooks write and the TUI, `taskman status` and `taskman resume` read (`Record`, `read`, `write`): every field may be missing or odd, an unknown state reads as idle, and the file is written byte for byte as before the struct; the words for each state (`HookState::word`) and the names of running sessions (`running_names`) |

## How the pieces fit

- **Sessions.** `App::launch` (used by the pane's `build_command` and by `taskman resume`) starts `claude` with `--name <key>` (`<project>/<key>` while another project has the key: `store::session_name`; other sessions message it by that name), `--resume <id>` when a transcript exists, `--append-system-prompt` (the ticket or agent brief), and `--settings` adding hooks that run `taskman hook <state>`. Hooks write `~/.local/state/taskman/status/<project-id>/<KEY>.json` (`store::status_file`), which `poll_status` reads; each start passes `TASKMAN_LAUNCH`, which the hook records, so a hook of an earlier start writing late isn't taken for the running session's (`TicketView::takes`). A ticket is its project's main checkout and its key (`Ticket::is`): keys repeat across projects, so never look one up by key alone. The user's own Claude settings are never touched. A ticket with `cli: Codex` starts `codex` instead (`session_args`): the same hooks as `-c` overrides with their trust hashes (`hook::codex_config`), the brief as `developer_instructions`, and `codex resume <id>`. Sessions get a `taskman` link to the running binary first on their PATH, and the briefs tell them to read their ticket with `taskman status`. The `--settings` permissions allow `taskman status`, `taskman add` and `taskman move` without a prompt (`hook::settings_json`), and in a session the three refuse any project but its own, the one in `TASKMAN_REPO` (`cli::confine`), since the rules can't tell arguments apart; an agent or role from `taskman add` still waits for the user's approval in the TUI. Text from trackers and PRs is untrusted: print it through `untrusted` and keep it out of briefs (see "Untrusted text" in [design.md](design.md)). Agents add tickets and other agents with `taskman add`, which leaves a request in the state folder's `inbox/` for the TUI (`take_inbox`) rather than editing `tickets.json`. A change to the request needs a new `add::INBOX_FORMAT`, so a command never asks an older running TUI for something it can't do. An agent's optional `role` (`Ticket::role`, kept on `ClosedAgent` too) is appended to its brief at every session start. Agents added through `taskman add` start their session once the user approves them (`App::ask_next`, then `TicketView::start`). `taskman close` uses the same inbox (a request with `close`); the TUI closes through the close dialog's code (`App::close_at`, then the removal check) and it's deliberately not on the allow-list.
- **Handed-off sessions.** `ctrl+a t` and `taskman resume` move a session between the pane and the user's terminal; `TicketView::away` says where it is, and `resume::Hold` (an `flock` on `<KEY>.owner` beside the status file) keeps it to one copy. Never start a session without `start_session`, which takes that lock.
- **Stopping sessions.** A stopped CLI takes a moment to go (hung up, then killed, on a thread): until it's reaped, the ticket's `reaper` (`TicketView::stop_session`) keeps a new session from starting, a closed ticket's worktree from being removed and, after a hand-off, the claim from being let go, the owner file reading `Owner::Stopping` meanwhile. See "Stopping a session" in [design.md](design.md).
- **Stacked tickets.** `Ticket::base` names the ticket a worktree started from; whether it merged comes from the base ticket's PR or from the ticket's own PR's `baseRefName` (`App::stack_of`).
- **Background work** runs on plain threads and reports back over an `mpsc` channel (`Msg`); there is no async runtime. `Remote<T>` holds fetched data with its freshness and refresh flags. Keep network calls and token commands off the UI thread; commands go through `proc::run` so a hung one gives up.
- **Accounts vs projects.** An account is credentials (`store::Account`, id like `jira-1`); a project's tracker names its account or falls back to `Config::account_for`. Tokens are never stored: `env:VAR`, `cmd:COMMAND` or `keychain:NAME`, read in the background by `tracker::Clients`. The account form can write a pasted token to the keychain first (`keychain::Keychain::store`), or where there's none to a private file read by a `cmd:cat` (`token_file::store_in`), in its background check.
- **Trackers.** Fetching goes through `tracker::Client`, and each difference between providers is a method on `Provider` or `Tracker` in `tracker.rs` (`needs_account`, `has_board`, `branch_source`, ...): use those rather than matching on a provider. `Account::who` and the account forms' Provider field still match on it. A new provider is a `store::Provider` variant, its API module, a `tracker::Client` variant, one arm per method in `tracker.rs`, and its account form fields.
- **Modes.** `Mode` decides where keys go: Claude (Normal), a form, Settings, or a confirm dialog. Every key goes to Claude except after the prefix (`ctrl+a` unless changed). Hints name it through `keys::prefix()`, never a literal `ctrl+a`.

## Invariants

What must stay true whatever changes. Each has a section in [design.md](design.md) saying why.

- **A ticket is its project and its key** (`Ticket::is`). Keys repeat across projects, so nothing looks a ticket up, names its status file or claims its session by key alone. An agent is found by its project and name (`Ticket::is_agent`, `store::find_agent`), not by a key made from the project's name: `store::agent_key` makes the key only when an agent is added or renamed, and a renamed project keeps its agents' keys.
- **One copy of a session.** Every session starts through `start_session`, which takes the owner lock (`resume::Hold`); a pane and `taskman resume` never run the same session at once, and a lock that can't be taken stops the session starting. The lock is taskman's, not the CLI's, so a session also starts only once the last one's CLI is reaped (`TicketView::reaping`), and a hand-off keeps the lock until then. `taskman resume` finds sessions in the saved state, so a rename, close or project removal saves first (`App::try_save`) and is undone when the save fails, its claims kept.
- **One conversation per session.** `session_ids::claim` refuses an id another ticket or agent holds, wherever an id comes in.
- **The user's own CLI settings are never touched.** Hooks and permissions come in through `--settings` (Codex: `-c` overrides) on each launch.
- **Tracker and PR text is untrusted.** It's printed through `untrusted` and never goes into a brief, since anyone who can write a comment could write instructions.
- **Tokens are never stored.** Accounts say where a token comes from (`env:VAR`, `cmd:COMMAND` or `keychain:NAME`); it's read in the background when needed. A token pasted into the account form lives in the form only until it's in the keychain, or in a private file whose `cmd:cat` the account saves.
- **Nothing slow runs on the UI thread.** Network calls and token commands run on threads; git, gh and token commands go through `proc::run`, with a time limit and no terminal.
- **Saved state is never replaced by less.** Only a missing file reads as empty; a file this build can't read, or of a newer `store::FORMAT`, stops the TUI rather than being overwritten. New fields get `#[serde(default)]`; fields a build doesn't know are kept in each struct's `extra` and written back, and code that rebuilds a saved struct carries its `extra` over.
- **Sessions change the TUI's state only through the inbox.** `taskman add` and `taskman close` leave requests for the running TUI instead of editing `tickets.json`; a changed request gets a new `add::INBOX_FORMAT`.
- **Provider differences live in `tracker.rs`,** as methods on `Provider` or `Tracker`, not as matches on the provider elsewhere.

## Cross-cutting concerns

- **Threads and messages.** There is no async runtime. Background work runs on plain threads and sends a `Msg` over an `mpsc` channel; `drain_messages` applies them on the UI thread each tick. `Remote<T>` (in `app/sync.rs`) is fetched data with its freshness and refresh flags, so a ticket never starts a refresh while one is in flight, and the id of its latest fetch, so a reply that lands after the tracker changed or the ticket was closed and added again is dropped rather than shown as fresh. A thread whose message something waits for starts through `Reporter` (`App::reporter`), which catches a panic in its work and sends the failure instead, with an error toast pointing to `panics.log`.
- **Status files and hooks.** A session's state comes from the files its hooks write under the state folder's `status/<project-id>/`, read by `app/poll.rs`; each record names the start of the session that wrote it, and the pane takes only its own start's. When no hook fires (an approved permission prompt, an interrupt), the state is inferred from keys and the screen.
- **The owner lock.** `<KEY>.owner` beside the status file, held with `flock` by whichever process runs the session (the TUI or `taskman resume`), by the TUI after a hand-off until the pane's CLI is reaped, and by the git removing its worktree; the system releases it however the process ends. It's taken before every start and fails closed: without it, the session doesn't start.
- **The inbox.** The state folder's `inbox/` carries requests from the CLI commands to the running TUI and the TUI's replies back; `inbox/alive` is the TUI's heartbeat (written whole and renamed into place, so a command never reads it half written) and says which request formats it understands, so a command knows whether anything will answer and what it may ask.
- **Testing layers.** Unit tests sit next to the code; pure decisions (parsing, matching, ordering) are extracted so they can be tested where they live. Code that parses others' text has `proptest` properties too. `app/test_support.rs` builds an `App` on a mock project with nothing started; `app/events/` drives it with keys, mouse reports, pastes and messages; `ui/screens.rs` compares what's drawn with `insta` snapshots. The tracker clients are tested against recorded responses in `tests/fixtures/`, served by `replay.rs` (GitHub Issues' by its test runner); no test reaches a real tracker or runs gh for one; the PR lookup's unit tests pass `fetch` a gh that answers from the same fixtures. What needs the real binary (the terminal, signals, a CLI's process, hooks, the clipboard and browser commands) is in `tests/`, which runs it in a pty with stub CLIs, its own home, and stubs for gh and the keychain tools first on PATH, so no test reaches the developer's own login or keychain.
